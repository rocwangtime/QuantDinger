## 1. 首要纠正：故障时 shard3 并非 ETH 5m 单独连接

采样末尾的 `[2,2,2,2,10,12,12]` 是**管理器重建后的布局**，不能反推此前 40 分钟的布局。06:20:26 至 07:00:33，资料中的热门分组实际为：

| 分片 | 实际分组 | 当前资产数 |
| --- | --- | --- |
| shard3 | BTC 5m + BTC 15m | 4 |
| shard5 | ETH 5m + ETH 15m | 4 |

五次主路 1013 的 transport evidence 都记录 shard3、`assets=4`；连接年龄分别为 **209.068、622.145、86.692、1506.172、22.307 秒**。固定窗口内，transport evidence 一共记录 **shard3 主路 5 次、shard3 备份 8 次、shard1 备份 1 次**。所以 shard3 合计 13 次，全部分片合计 14 次；分析摘要里单独匹配 close 行得到的“主路 3 次”少于 transport evidence，不能作为完整故障计数。

代码里的 `forced_hot` 原先只是搜索目标的一部分。初始放置先按资产容量和估计负载安排，未知组的权重接近 1；“热门组互不混订”没有结构优先级。后续只在完整、健康的测量窗口里规划迁移，而实际持续积压使这些窗口被冻结。结果就是热门组长期挤在同一条连接，不能期待测量器自动及时拆开。

本轮在新组放置和搜索评分中，将**已指定热门组与任何其他组的混订数**置于容量/负载收益之前；新组先放热门组。没有速率先验、所有先验一样，或冷门权重很高时，四个热门组也各占一条连接。YES/NO 仍不可拆。17 个普通市场加四个热门组的测试布局需要 7–8 个主分片，沿用最多 8 个的上限。

这不是承诺单对 YES/NO 永远低于带宽预算：一组本身过热时保留该组并明确报告不可拆分超额，不能通过慢读或隐藏超额来“达标”。

## 2. drops=116803：确有反复本地溢出，但不是那一秒清了 11 万帧

`ReceiveQueue.dropped` 是**单连接代次累计数**，混合了队列满时拒收、resync 期间拒收、恢复时清空 FIFO，以及断连退出时清空 FIFO。队列上限是 16,384，不可能同时存着 116,803 帧。

同一个 1506 秒代次有以下恢复记录：

| SGT | 累计 drops |
| --- | ---: |
| 06:37:27 | 16445 |
| 06:38:04 | 32958 |
| 06:38:57 | 49357 |
| 06:39:20 | 65775 |
| 06:40:41 | 82251 |
| 06:56:33 | 98640 |
| 06:57:54 | 115173 |
| 07:00:14 断连失效 | 116803 |

前七条与反复填满约 16,384 帧后恢复完全吻合。最后相对 115173 增加 **1630**，不是新的一次 11 万帧清理。旧计数不能精确区分这 1630 帧里断连残留与拒收的比例。固定窗口内备份采样队列深度最高 **15942**，排队时间最高 **30.525 秒**；主路也有上述多次溢出，不能把 `ingress_pressure` 全解释为阈值误报或 initial snapshot 短暂突发。

本轮拆分代次内 `drop_reasons`：`overflow`、`resync_rejected`、`invalid_rejected`、`resync_discarded`、`shutdown_discarded`。总和等于该代次的 dropped；这些分类不是跨进程持久化累计。主路、B/R 指标及故障 evidence 都带原因、resyncs、队列高水位和等待时间。

清理 FIFO 改为在队列 mutex 内交换有界 deque，之后释放旧帧，减少逐帧 Queue API/锁开销，避免生产者持续补入延长清理循环。交换为常数时间，**释放对象仍是 O(n)**，不能宣称 GC/内存释放完全不耗时。另报 `discard_max_seconds`、`process_max_seconds`、备份 `lifecycle_wait_seconds`，用于区分清队列、worker 处理及生命周期/发布锁等待。没有扩大接收队列，也没有放宽就绪的 1 秒新鲜度要求。

## 3. 07:00:39–41 七片一起关闭：本地全局 REST fallback

原主循环每次把 `connections.failures()` 的值写入 `ws_failures`。前者返回**尚未 connected 的分片中最大 attempts**，不是全体连接故障数。下一轮 `ws_failures >= 3` 就执行 `connections.close()`，依次关闭所有主路和备份、清理实时盘口并转一次 REST；之后又创建全新的 MarketConnections。

07:00:14 的长寿命连接关闭后，attempts 重设为 1，新连接递增到 2；07:00:38 的短连接又失败，下一次重拨可递增到 3。在握手完成前主循环采到这个值，就会在下一轮关闭整个管理器，即使新连接此时已经成功打开。这解释了 **07:00:39 shard3 已 open，紧接着七片逐个空 reason / code=None 关闭，07:00:57 起整批重新 open** 的时序。专项主循环回归用一个分片 12 次重试复现旧触发条件，验证现在继续复用管理器，不进入全局 REST capture。

关闭前的心跳证据也不支持“清理 drops 卡住全进程几十秒”：

| 故障时刻 SGT | ping/pong | PONG 年龄 | 当前采样/最近窗口调度证据 |
| --- | --- | ---: | --- |
| 07:00:14 shard3 1013 | 150/150 | 3.137 秒 | 最近 60 次采样最大 lag 0.00321 秒；TCP pending=0 |
| 07:00:38 shard3 1013 | 2/2 | 1.540 秒 | 最近窗口最大 lag 0.00464 秒；TCP pending=24 字节 |
| 07:00:39–41 其余旧主路 | 244/244，shard2 为 70/70 | 1.917–7.806 秒 | 最大约 0.0971 秒，无几十秒采样洞 |

新开的 shard3 才存活约 1 秒，还没有首个 PING，不能把其 0/0 解释为心跳失败。观察器是多条 reader/worker/heartbeat 线程，并没有一个承载全部 WS 的 asyncio 事件循环。采样不能排除所有短暂 GIL/日志/GC 停顿，也不能定位全部 CPU 成本，但本地全局 fallback 的代码路径、依次关闭和指标重置共同构成更直接的解释，不能把这一组关闭当作已确认的远端/IP 级故障。

本轮不再用分片 attempts 触发主循环全体切换；已运行管理器的 socket 恢复交给每片 supervisor，既有按需公开 REST 快照恢复继续工作。初始化失败前的主循环错误退避仍保留。主动关闭新增 `manager local shutdown` 日志，关闭期间的 on_error/on_close 不再伪装成远端故障或计入热门故障数。

## 4. 热门备份：真实积压、字节预算与一条/两条的取舍

固定 81 个样本里 BTC 两组各有 **55 个 0/2**，ETH 两组各有 **42 个 0/2**；B 阶段统计为 `ingress_pressure` 91、`subscribe` 12、`ready` 61。07:00:33 之前 BTC 5m 的零备份时间中，**steady 有 1311.463 秒**，换期前 21.437 秒、换期后 343.559 秒；BTC 15m 的 steady 有 1564.346 秒。故障覆盖不了的时间大量发生在平稳阶段，不能只归因于追初始快照。

当时主路+两备份对同一热门组复制三份流量，并各做影子/合流/连续性等处理；容器 CPU 中位约 108%，进程 CPU 中位约 1.016 核。持续 FIFO 积压和反复溢出证明本地处理吞吐不足以持续追上这些副本；缺少生产 profiler，尚不能把 GIL、JSON、指纹、各个锁和 GC 分别归因到百分比。混订热门组、三份重复工作及预热额外资产都可能放大成本，不能只调整 `queue_depth > 32` 的订阅准入阈值来制造 ready。

本轮采用：

1. **默认一条备份**，配置 `POLYMARKET_OBSERVER_WS_HOT_BACKUP_COUNT=2` 可显式保留两条做后续对照；允许值钳在 1–2。`target_backup_count` 报真实目标，补充备份/故障提升路径保留。
2. 每条物理连接都采样实际接收字节速率，至少 1 秒一个窗口；备份不再只有累计 bytes。对只有一个组的主连接，可直接归因 raw ingress bytes，即使 worker 排队也不会把该组学习成低带宽。规划取 raw 采样与原已处理字节估计的较大值，暴露 `ws_group_ingress_byte_rates`。
3. 沿用已有 **262144 B/s** 默认规划预算。当前主路、任一备份或已归因的该片字节负载达到预算，就不再给备份加下一场次预热；若已经预热则退掉额外资产。按当前资产集合锁存这个决定，防止一两个安静 tick 反复订退下一快照；换到新的当前资产集合后重新决定。过热时每条热门连接保留当前 YES/NO 对。
4. 订阅准入的 queue-depth、queue-lag、resync、gap、TCP pending 和 scheduler-lag 阈值保留，新增 `admission_pressure_reasons`。它解释的是**订阅准入**阻塞，不与备份就绪判定混为一个指标；当前完整且追上的备份仍可 ready。真实排队超 1 秒仍不 ready。

按用户指出的每连接 650 KB/s–1.2 MB/s 流量估算，同一组从三份减到两份，聚合负载从 **1.95–3.6 MB/s 降为 1.3–2.4 MB/s，减少 1/3**，本地重复处理份数也少 1/3。这是副本数的算术，不是生产 CPU 或 1013 已改善的实测结果。单次 close 采样甚至出现约 1.52 MB/s，而其 60 秒总量相当于约 709 KB/s，说明必须区分瞬时与窗口速率。

代价是只剩一条备份时，该备份自身被踢便暂时零覆盖；原先两条都健康时可以再承受一次故障。当前 BTC 55/81 采样两条都不可用，继续默认加第三份热门流量的收益证据不足，因此先减少重复工作，同时保留两条对照选项。**没有同 IP 单备份/双备份的生产对照，不能声称已证明远端有 IP 带宽限额或一条备份能降低 1013。** 一对资产本身超过预算时不慢读、不丢掉其中一边来伪造限速，超额继续可见；这仍是准入/布局预算，不是官方公布的硬限制。

## 风险与部署后应观察的指标

本轮未部署，没有 round12 生产验收数据。只减少并定位可解释的本地放大因素，不能保证 1013 消失或始终有备份。

1. **布局**：启动、5m/15m 换期后，四个热门组各自独占，YES/NO 同片；热门组不与其他热门/普通组混订。过热时 backup 的 `prewarm_assets=0`，正常预算内可预热；`indivisible_excess` 允许非零，`co_tenant_excess` 应消除。对照 raw ingress 与旧 group bytes，不能继续用慢 worker 的低处理率宣称容量充足。
2. **单备份取舍**：确认目标为 1，记录 ready 数为 0 的时间、每连接小时的 1013、主路故障时 ready 数、接管/REST 恢复耗时和冷门新鲜度。比较至少多个完整换期窗口、相近流量，再决定是否试显式两备份。不要只比较 0/2 与 0/1 的分母，也不要从一个窗口推断 IP 限额。
3. **局部故障隔离**：热门主路连续失败时，冷门连接年龄不应一起归零，管理器 session 的 group 故障数、1013 数、zero-ready 累计应单调。若发生主动管理器关闭，必须有 local-shutdown 日志；进程真正重启则按新 session 分段。
4. **积压与慢读区分**：对照 `queue_depth / queue_wait_seconds / high_water / drop_reasons / resyncs`、`process_max_seconds / lifecycle_wait_seconds / discard_max_seconds`，以及 close evidence 的 60 个 transport 样本、PING/PONG、TCP pending、scheduler lag。新增计时含等待，不是 CPU profiler；如积压依旧，需要据此再选择 profiler 或锁分析，不能据本轮无生产采样的代码推断已解决所有 CPU 瓶颈。
5. **换期风险**：超过字节预算时禁掉下一场次预热，会用更长的换期零覆盖换取较低的流量/处理压力。检查 zero-ready 的 before/after/steady、首次新快照时间和主路恢复；若换期损失明显恶化，再用实测重设预算。没有提高就绪门槛容忍度。
6. **内存与恢复**：持续观察 RSS 的峰值和跨换期基线，以及去重 entries、shadow/merge assets/levels、接收队列、退役连接和解析缓存。全局重建消失后应重新看长期基线，不能依赖重建来降 RSS。继续检查公开 REST requests/failures/throttled 和冷门 delivery latency/update silence，避免将压力转移到恢复通道。

启动后维持“公开行情观察、纸面自动交易关闭”的现有安全配置；本轮没有执行部署或修改部署环境。
