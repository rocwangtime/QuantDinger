## 原因与改动

### A. 热门组保留两条备份，修复就绪与补建链路

代码中确认了以下会放大未就绪时间的链路；现有汇总采样不足以把历史每一秒未覆盖都精确归因到其中某一项：

1. 备份最后一帧处理曾超过 1 秒时，旧 `queue_wait_seconds` / `delivery_gap` 可能在队列已经排空后仍保留。缺快照重试又会先退订，再进入受 `ingress_pressure` 约束的共享订阅队列，形成长时间未就绪的路径。
2. 缺快照重试以 10 秒为周期，且会拆掉已有订阅；每次重试都可能重新等待订阅额度和快照。
3. 首条备份故障或被提升后，年轻存活连接仍受原来的 90–120 秒年龄门槛约束。连续失败的备用退避还可升至 30 秒。
4. `stage=ingress_pressure` 原先也可能与 `ready=true` 同时出现，阶段字段不能直接解释为“备份不可接管”。

本轮行为：

- 每个热门分片目标为 **主路 + 两条独立备份**。第一条备份及唯一备份缺失时尽快补建；第二条相对第一条初始订阅错开 **10–15 秒**。没有就绪备份的组优先于已有一条备份的组。
- 移除补齐唯一备份时的 90–120 秒年龄等待；热门备份失败重试保留随机退避，最长压至 2 秒。不同组仍共用连接/首帧准入间隔，按实际初始订阅完成时间计时，避免延迟握手后同时放行。
- 两条备份只复制该主分片已有的资产集，不把热门组加到其他已有连接上；单连接订阅负载没有因此增加。两条备份都参与原有时间水位保护和事件去重，任一可接管，故障一路不会抹掉另一路的覆盖状态。
- 缺快照检查缩至 0.5 秒，通过独立 REST 修复；不再为热门备份补快照先退订。换期仍正常退订过期资产，并同步更新两条备份。
- 备份 worker 在队列确实为空时清除历史排队延迟；真实丢包仍由 resync / epoch 屏障处理。就绪仍要求完整快照、有效交易所时间、订阅完成、代次有效、无重同步/待恢复资产，排队延迟不超过 1 秒且没有 delivery gap。
- 已经满足就绪条件时，诊断阶段显示 `ready`。这没有把缺快照或真实积压改算成就绪。备用连接的压力、缺 PONG 或预热耗时仍不会被当成远端断线而反复销毁重建。

### B. 无就绪备份时，REST 与新 WS 并行恢复

旧监督逻辑只要发现备份仍连接着，就会跳过主路重连，即使该备份一直没有完整盘口。本轮取消这条阻挡：

- 主路错误/关闭回调按代次去重记录故障；若没有就绪备份，立即清除失效的实时盘口，并启动独立公开 `POST /books` 修复任务。
- 新 WS 不等待预热备份，也不等待旧 reader / worker 的各 5 秒 join；使用独立状态建立新代次，保留原有连接重试随机退避。预热备份继续接收，谁先有可用数据就先恢复盘口。
- REST 不占用接收线程或监督循环。连接/读取超时分别为 0.4、1 秒；一次只请求该连接需要修复的资产。最多 4 个并发、每状态最多 1 个在途请求、重试间隔至少 0.5 秒，观察器管理器共享 **40 请求/10 秒**的滑动窗口预算。本轮不调用 `/book`，为 `/books` 官方 500/10s 留出大量余量。
- REST 禁用环境默认认证与重定向，不使用 CLOB 凭证。响应必须包含完整且不重复的目标资产、有效时间和盘口结构；超过 2 秒的新鲜度范围或无效响应不发布。
- 发布前检查连接身份、retired 标记、接收代次和 epoch；已退订资产、重同步前发起的响应、旧连接晚到响应不能写入新盘口。REST 与 WS 共用时间水位保护，较旧快照不能覆盖已收到的较新盘口或增量。
- 失效旧 worker 的清理不会再次删除本次故障之后已恢复的盘口。REST 恢复也进入连续性记录，但不会被宣称补回了历史成交。

这是把原有串行等待改为并行竞争，**不是对线上每次恢复低于 2 秒的保证**。正常网络下的测试覆盖了 WS 仍离线时先由 REST 在 2 秒内恢复；持续网络故障、上游排队、反复握手失败的退避、调度阻塞均可能超过目标。

### C. 按热门组记录被踢时备份与接管耗时

新增/扩展状态如下，均为本观察器会话累计：

| 指标 | 口径 |
| --- | --- |
| `ws_hot_primary_failures[group].total` | 该组主路故障累计次数，包含 1013 和 code=None 等断连；同一代次 error/close 去重 |
| `without_ready_backup` | 故障发生时没有就绪备份的累计次数 |
| `events[].code` / `ready_backup_at_kick` / `ready_backups` | 每次故障的关闭码、当时是否有就绪备份及条数；最近最多保留 64 条事件 |
| `events[].takeover_gap_ms` | 从发现故障到可用盘口恢复或备份提升的耗时；未恢复时为 null |
| `events[].receipt_gap_ms` | 恢复时刻与故障前订阅资产中最早的末次盘口接收时间之差，是保守接收跨度；包含自然静默，不能当作逐条丢包证明 |
| `events[].recovery` | `backup`、`rest_snapshot` 或 `ws` |
| `ws_hot_backup_by_group[group].time_without_backup_seconds` | 保留原有按状态转移积分的累计无备份秒数，跨换期保留系列身份 |
| `ready_backup_count` / `target_backup_count` | 当前可用备份数及目标 2 条；历史覆盖率仍按“至少一条备份且主路可用”计算 |
| `ws_reserves` | 第二条备份的连接、就绪和阶段状态；第一条仍在 `ws_backups` |
| `ws_rest_recovery` | 请求、完成、失败、在途、限流次数及本地 40/10s 预算 |

`ws_rest_recovery.completed` 代表有效响应完成发布尝试；被代次屏障丢弃的结果不能据此认定恢复成功，应核对故障事件的 `recovery` / `takeover_gap_ms` 和实时盘口。原有 `ws_primary_1013_by_shard`、接收队列、传输证据和 `ws_continuity` 保留。

### D. 容量超限是真实预算超限，补齐可解释口径

原指标由**逻辑主路归属的组级 EWMA**计算，不会因为两条备份或迁移中的物理重复订阅而直接翻倍。30 秒巡检也可能重复看到同一份 60 秒采样估计；49 个非零样本不是 49 次独立超载事件。

采样例子：早期 shard2 约 **770.085 msg/s、495418.473 bytes/s**，相对 300 msg/s、262144 bytes/s 的预算，恰好得到 **470.085 msg/s、233274.473 bytes/s** 超限；后续只剩 2 资产时仍约 **674.207 msg/s、440113.743 bytes/s**。一个不可拆分的系列本身就超预算，增加空分片或拆开 YES/NO 不能合法消除这个事实。

所以没有把 `ws_capacity_excess` 强行改成零，没有提高阈值，也没有重新拆腿。本轮修正其展示可解释性：

- `ws_capacity_scope=logical_primary_planning_budget` 明确这是逻辑主路的本地规划预算，不是官方限额或实时队列故障计数。
- `ws_capacity_by_shard` 列出每片组名、超限总量、完整系列自身的 `indivisible_excess`、额外同片负载贡献的 `co_tenant_excess`，以及没有测量样本的 `estimated_groups`。
- 原有按健康采样、滞回与冷却进行的整组迁移继续处理可迁移负载。不可拆分系列自身超限会继续如实报告；本轮没有足够证据通过改变订阅语义来降低这部分源流量。

## 风险与部署后观察

本轮未部署，没有新的生产验收数据，不能宣称零缺口或覆盖率已经达到目标。

1. 四个热门组稳定后检查 `ready_backup_count=2`；第一条应尽快就绪，第二条应在错峰准入后就绪。重点看覆盖率是否接近 1、`time_without_backup_seconds` 的增长速度、备用重建耗时，而不只看 connected 数。
2. 每次主路 1013 / code=None 都核对 `ready_backup_at_kick`、备份条数、`takeover_gap_ms`、`recovery`。目标是有备份时连续接管、无备份时尽量在 2 秒内恢复；任何无备份故障、null 长时间不消失或超过 2 秒均需追查。结合逐资产 `ws_continuity`、盘口缺失和新鲜度判断，不能把接管毫秒数当成成交逐条完整的证据。
3. 观察备用 1013 后是否及时补齐；多个组是否错峰，是否再次长期停在 subscribe / snapshots / ingress_pressure。检查 resync、delivery gap、队列等待、调度延迟与 TCP backlog，避免额外副本导致本地处理压力。
4. 热门组从两路变三路，总带宽、解析 CPU 和去重开销会增加，虽然单连接资产集未增加；上游 IP 连接数限制未文档化，三路也可能相关故障。必须对比 CPU、队列丢弃、1013、1008 和冷门新鲜度，不能仅看备份覆盖。
5. 检查 `ws_rest_recovery.failures/throttled/inflight`、实际恢复事件及 HTTP 尾延迟。40/10s 只约束本管理器新增恢复流量，不协调同 IP 其他进程；连接/读取 timeout 也不是整个请求的硬总耗时上限。上游不可用或限流时仍可能超过 2 秒。
6. 对照 `ws_capacity_by_shard` 区分完整热门系列自身超预算、同片其他组与估计值。不要把 `ws_capacity_excess` 非零直接解释为“备份重复计数”或“必须立即迁移”。完整系列超预算仍是已知限制。
7. 跨过多次 BTC/ETH 5m、15m 换期，确认两条备份资产集都更新、YES/NO 同片、过期资产均退订，且旧代次/旧 REST 响应不能恢复已移除盘口。两路同时失效、没有就绪备份或调度/网络阻塞时仍有缺口风险；REST 快照不能补回缺失的历史成交。
