# Polymarket WS 第 3 轮（2026-10-17，仅纸面，未部署）

## 结论

基线为 `fix/pm-ws-stability` 的 **cc1362515bb96f803492b6202b8213fc480e6ef4**。本轮直接在此分支提交和推送，不开 main PR，不合并、不部署。SSH 仅用于只读的日志、SELECT、ss、进程和 cgroup 检查，没有改线上参数或重启服务。

**没有证据足以唯一确认 p34 的 slow_consumer 根因，更不能宣称已经根治。** 本次捕获到一次新的自然关闭，提供了比事后空队列更强的证据：关闭前约 750ms，相关 TCP 连接 Recv-Q 仅 **637B**，其接收缓冲约 **400KiB**，且连接仍持续收取数据。这不支持“本机接收缓冲持续满、窗口一直耗尽”的解释。剩余方向是远端扇出/WS writer/edge/origin 路径的拥塞或瞬时调度/网络停顿；单秒 ss 采样无法完全排除短于采样周期的本地停顿，也无法看见 edge 到 origin 的链路。

有直接代码与回归证据支持的本地缺陷已修复：**心跳依赖可能执行 HTTP、retention、SQL 的市场主循环；websocket-client 1.9.0 的关闭帧在 on_error 路径丢失 code/reason；监控各阶段缺少可靠的硬期限，且 TCP 采样被串在慢 SQL 后面。** 这些修复不等于已经证明它们导致了远端 1013。未继续扩大应用 FIFO、默认连接数或盲目提高 SO_RCVBUF。

## 各排查方向

### SO_RCVBUF、窗口和真实吞吐

线上 `tcp_rmem=4096 131072 6291456`，`tcp_moderate_rcvbuf=1`，window scaling 开启；host `rmem_default/rmem_max=212992`。实际行情 socket 的 `ss skmem rb` 为 346503、369043、409185、2044194 等，说明自动调节已经生效，不能用 host 默认值认定每条连接只有 128/212KiB。[Linux TCP 文档](https://man7.org/linux/man-pages/man7/tcp.7.html)区分了自动调节与应用显式设置接收缓冲；手动 SO_RCVBUF 会限制这条连接的自动调节，普通 setsockopt 还受 rmem_max 限制。因此“设置 4MiB”也可能被截断为约 416KiB 的报告值，反而比已经调到约 2MiB 的连接小。

`rcv_space` 是接收侧自动调节相关估计，**不是当前对外通告的可用窗口**；`snd_wnd` 是对端窗口，不能当作本机接收窗口。新代码按 [Linux UAPI tcp_info](https://github.com/torvalds/linux/blob/master/include/uapi/linux/tcp.h)读取内核实际提供的字段，包含 `rcv_wnd`（版本支持时）、`rcv_ssthresh`、`rcv_space`、window scale、SO_RCVBUF、FIONREAD。短结构只报告有的字段，不用 0 冒充未知。

吞吐使用 `bytes_received` 差分，而不是 ss 的 `send ...bps`：02:41–02:45 最热端口 49900 采样峰值约 **1.302MB/s（10.4Mbit/s）**，累计接收约 93.75MB。它的 Recv-Q 峰值 73186B，rb 2044194B。多个其他连接也超过 128KiB/s，**没有证据支持此前模拟反例里的 128KiB/s 是 Polymarket 的真实限速**。这些 TCP 字节含 TLS/WS 开销，也不等同于应用消息体字节。

新 `transport.read_bytes_per_second` 来自实际预读 `_recv` 返回字节的差分，包含 WS 帧头、control 帧与尚未回调的预读数据，是 TLS 解密后读取层指标。原有 receive_bytes_per_second 是 on_message 消息体，两者与 TCP 入站字节必须分开解释。fallback 未启用预读时同时查看 read_ahead_active，不把读取计数当作完整覆盖。

`POLYMARKET_OBSERVER_WS_RCVBUF_BYTES=0` 保留自动调节。正值仅供显式诊断实验，实际值以 getsockopt 为准；本轮没有在线设置它。

### CPU、GIL、事件循环与 scheduler

02:40 observer 为约 **24.71% CPU**，scheduler 0.11%；vmstat 短窗口 idle 80–86%。08:24 observer cgroup `cpu.max=max 100000`、`nr_throttled=0`、`throttled_usec=0`。这些不是关闭瞬间的 profiler，不能排除短暂调度停顿。线程 CPU 原始样本保存在 ss 流中，也不能当作 GIL 持有者追踪。

实际 observer 命令为 `python -m app.commands.polymarket_observer`，scheduler 为独立容器里的 `python -m app.commands.scheduler`。**scheduler 不与独立 observer 共享 Python GIL**，但共享机器 CPU/内存/I/O。observer 内的 writer、evaluator、book worker、reference 与读线程仍共享 GIL，JSON 编码和业务线程的 CPU 工作仍可能影响调度。本轮没有附加 profiler 或改 scheduler、writer/maker 行为。

新每连接 heartbeat 线程每秒采集 transport，保留最近 60 条；sample_gap_seconds/scheduler_lag_seconds 是这个线程的实际调度间隔，**不是唯一归因的 GIL 时间**。ws_tick_gap_seconds/max 单独反映主循环 tick 停顿。两者配合外部 ss，区分主循环被 HTTP/SQL 占住、进程整体停顿、socket 读取变慢、上游停止交付。错误回调在库清空 socket 前补采一次并写出有界历史，断线后的状态保留最后失败样本。

### ping/pong 与 TCP keepalive

[官方公共 WS 指南](https://github.com/Polymarket/agent-skills/blob/main/websocket.md)要求每十秒发送文本 PING。原代码 `ping_interval=0`，仅在 MarketConnections.tick 里发送；该 tick 与发现目录、retention、状态持久化共用市场线程，代码上确有迟发风险，但旧指标没有 PONG RTT，无法证明历史 1013 是心跳故障。

现在复用 WebSocketApp 的每连接 ping 线程生命周期，改为独立发送**文本 PING**，不依赖市场 tick。保留库对控制 Ping 的自动 Pong，应答文本 PONG 时记录次数、RTT 和 age；不额外用无证据的 PONG deadline 触发重连。keepalive 沿用 websocket-client 1.9.0 的默认 SO_KEEPALIVE/TCP keepalive 配置；新指标报告实际 SO_KEEPALIVE。[库源码](https://github.com/websocket-client/websocket-client/blob/v1.9.0/websocket/_socket.py)中的 TCP 探活不能替代交易所的应用文本心跳。

本地真实 TCP/WS 回归验证帧 opcode=1、masked payload=PING，随后 PONG 与真实 1013 正确交付，ping 线程在库 teardown 后退出。发送失败会通知错误回调并 shutdown 唤醒读线程。

### 订阅资产数、服务器上限、压缩与进程方案

02:40 资产分布 **36/2/2/8**，估算负载约 **338/804/390/584 msg/s**；最早四次关闭都在已只订阅两个资产的 shard 1，不能继续把资产数多作为充分解释。02:42 的 shard 3 也失败，说明不是 shard 1 固定索引专属问题。公开协议未找到这条错误的队列容量、每连接字节上限或服务器内部组件定义。每连接 600 资产是本项目的自动增长目标，**不是已确认的交易所硬限制**。

[websocket-client 官方说明](https://github.com/websocket-client/websocket-client)明确目前不支持 permessage-deflate；当前客户端不请求该扩展，新指标暴露实际握手 extensions。本轮没有伪造扩展 header 或切换 WS 库：只加 header 无法获得解压支持，换库还需验证流控、碎片帧、TLS、快照恢复及服务端是否协商成功。压缩可能节省字节，也增加 CPU，并不能保证解决按消息数量计的远端队列。

保持市场/系列及两腿整体归属时，一个热点组已独占 socket，加空闲连接不能降低其单连接输入。单进程多连接共享 GIL，但当前没有证明 GIL 是关闭主因。多进程可隔离 GIL，却需要 IPC、生命周期和快照失效协议，不能改变同一服务端连接组的单连接流量，也可能放大总订阅量。本轮保留四连接和现有所有权规则，没有拆腿、复制订阅或引入多进程。

[Polymarket 官方仓库 issue #122](https://github.com/Polymarket/rs-clob-client-v2/issues/122)还有其他使用者的只收计数客户端复现，部分追踪无持续零窗口；这是独立使用者的一手观察，**不是维护者对服务端缺陷的确认**。结合本次关闭前 TCP 队列很小的证据，上游/路径方向值得进一步排查，但不能据此宣布找到了具体远端队列。

### RTT、丢包和重传的边界

关闭 socket 采样 RTT 约 4.976–15.459ms。ss 的 RTT 估计来自 TCP ACK，主要反映本机到 edge 的路径，不代表行情发布延迟或 origin 延迟。相同流的 skmem drops 在关闭窗口保持 2，不能把该字段当成端到端丢包率。

容器网络命名空间 02:41:03 到 02:45:39：RetransSegs **195→208**，OutSegs **1541146→1679786**，差分约 0.0094%。这是该 namespace 所有 TCP 的**出站重传/出站段比**，包括 HTTP/DB 等，不能证明行情入站没有丢包。关闭 socket 的 ss 未见 bytes_retrans 增长或持续 Recv-Q 饱和，但亚秒 incoming loss、edge-origin 队列、上游停顿仍不可见。没有使用 host 全生命周期 netstat 数字冒充这条行情连接的丢包率。

## p34_loop.sh 停采：确认的问题与没有确认的部分

原脚本在样本之间固定 sleep 120，慢请求的时间会叠加到周期；只有最外层 `timeout 90`，没有 kill-after、SSH ServerAlive、curl deadline、psql statement/lock timeout，也不记录样本结束/SSH 非零返回。命令通过 grep 管道输出，一个持有 pipe 的子进程也可能延长等待。SQL 与抓日志串行，完全没有短周期 TCP 流。

**这些是可复现的卡死/盲区风险，不足以证明 p34 02:13–02:29 空档的唯一直接原因。** 尤其已有外层 90s 限时，16 分钟空档也可能涉及本地执行环境暂停/不调度；旧记录没有 start/end/PID/monotonic heartbeat，无法再区分。本轮初始原始 SSH 流也只保留到 02:45:45，随后工具返回 server not responding；后续本地工具时间已跨到 08 点，不能用这段运行宣称已完成十分钟连续监测。

已修复并纳入分支的脚本：

- `p34_loop.sh` 使用自身路径定位脚本，任意 cwd 可启动；本地 `/workspace/quantdinger/deploy/` 同步副本也已更新。
- `p34_monitor.py` 两个独立采样通道，stdout 直接写文件，不依赖 grep 管道 EOF；子进程独立 session，超时 SIGKILL 整个本地 process group，回收后继续。固定 monotonic 周期，记录 start/end/returncode/timeout/missed/done，长暂停恢复后明确标注遗漏周期。
- 慢通道仅 observer 状态、health 和有界日志；curl 最长 4s、SQL statement 5s/lock 1s、docker exec 最长 12s，SSH connect/keepalive 和整体 deadline 均有界。移除旧监控的 maker、账户和 PAPER_AUTO 查询，不修改其代码或配置。
- 快通道在容器 netns 内约每秒 ss，每十轮 /proc/net 计数器；每个 SSH 会话最多采集 60 轮，外层最长 64s，独立轮转。会话轮转有数秒空档，不能说是连续无缝抓包。

脱离交互工具生命周期的启动示例：

```sh
nohup bash deploy/p34_loop.sh --duration 1800 --output deploy/p34_round3 \
  > /tmp/p34_loop.out 2>&1 < /dev/null &
```

nohup 只能抵御终端退出，不能保证被冻结/暂停的整台执行主机仍采样；如果需要连续故障证据，应在后续获准部署后依靠 observer 内部的有界历史，再结合持续运行的独立采样宿主。本轮没有部署，也没有在服务器安装定时器/后台服务。

12s 只读冒烟：慢通道约 3.88s 正常结束；TCP 通道按总运行预算在约 12s 被硬截止并记录 timeout/done。它验证脚本可运行及整体期限，不是稳定性时长验收。离线测试另外覆盖忽略 SIGTERM 的父子进程被杀、下一轮恢复、慢通道不阻塞 TCP 与 missed-slot 记录。
