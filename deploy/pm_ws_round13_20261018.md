## 1. 半死连接与已有双路合流

### 两次故障是同类下行停滞，但字节静默与应用数据静默应分开

- **09:02:33 BTC 5m / shard1**：主路最后应用行情约在 09:02:15；之后 1Hz 读字节为零，TCP pending 为零，PONG 不再增加。09:02:24 的发送仍获 TCP ACK，不能说明应用下行健康。连续性记录的旧主路静默为 **18327ms**，下一完整快照恢复记录为 **18682ms**。
- **08:05:03 BTC 15m / shard0**：最后应用行情约为 08:04:59.255，连续性旧源静默约 **4634ms**，随后完整快照恢复记录约 **5055ms**。采样在 08:05:00 仍读到约 42KB，08:05:01 起读零；因此它与前者同属应用下行停滞，但不能把它描述为整整 5.1 秒没有收到任何字节。主路排队仅约 0.254ms、无丢帧，不支持主路本地 FIFO 积压导致这次停滞。

原 `DataHealth` 需要学习带宽、足够连接年龄、连续低流量及健康 PONG，且有换期排除窗口。它是流量坍塌检测，不适合及时识别 PONG 也开始缺失的半死连接。本轮不缩短心跳间隔，也不以更频繁发送 PING 解决问题。

### 新增独立的字节静默接管

配置 **`POLYMARKET_OBSERVER_WS_HOT_BYTE_SILENCE_SECONDS`**，默认 **4 秒**，有效值钳在 **3–5 秒**。热门主路持续没有收到任何字节，同组备份已就绪、在主路静默后仍收到行情，且备份最近行情在 1 秒内，便标记 `byte_silence` 并提升该备份。提升继续由备份自己的 worker 执行，避免遗漏已从 FIFO 弹出、尚未发布的 delta。

实际 socket read（包括尚未组成完整消息的字节）与消息回调共同提供主路收字节时间；PONG 也会重置字节静默。备份是否在收行情使用独立的数据时间，不能拿备份 PONG 冒充行情。两路都静默、主路仍收字节、备份落后超过 1 秒、resync 或缺快照，均不会触发这一接管。

### 双路消费原本已经存在，本轮保留并验证，不新增第三份流量

`redundant_receive()` 在主路仍 connected 时就把备份数据交给共享 `FeedMerge`，主路 worker 也经过同一个 merge；这不是等判死才启用的冷备。因此原日志的 18.7 秒首先是**旧物理源到快照恢复的连续性区间**，仅靠这些日志不能证明合流盘口也整段没有写入。原指标与连续性检查使用不同来源，确有口径问题；不能据“22ms”判成功，也不能把“主路源静默”直接当作已测出的合流写入空白。

新回归明确验证：主路停收、尚未达到接管阈值时，备份 delta 已改变共享盘口；另一份相同消息不会重复发布，旧快照不能回滚新盘口。新增合流盘口 receipt 间隔/年龄指标，与物理源静默并列，供后续验收核对。接管时已存在且追上的合流盘口标为 `book_preserved`；历史事件连续性仍可 `unverified`，不捏造交易恢复或序列完整性。

默认仍是一条备份；没有增加连接副本数。文本 **PING 每 10 秒**的既有实现和 PONG 处理保持不变，符合已提供的官方规则。

## 2. 修复 takeover_gap_ms 的口径

旧 `record_primary_failure()` 从 `_PIPELINE.recording.metadata` 取最后 receipt。它是主备合流后的时间，健康备份持续写入时当然很新；而旧 `takeover_gap_ms` 又直接使用“判死到提升”的控制耗时。这两个字段都不能代表旧源停滞到恢复的区间，所以会出现 **22ms / 2.75ms 与 18.7 秒并存**。

现在每个热门故障事件保存旧物理源的最后 receipt，优先从连续性账本读取：

| 字段 | 新定义 |
| --- | --- |
| `source_silence_ms` | 检出故障时距旧源最后行情 receipt 的时间 |
| `takeover_gap_ms` / `receipt_gap_ms` | 同一旧源 receipt 到恢复的保守区间，两者一致 |
| `detection_to_takeover_ms` | 原控制耗时，独立保留，不再充当缺口 |
| `merged_receipt_gap_ms` | 故障检出时合流盘口的 receipt 年龄 |
| `gap_final` | 尚待连续性恢复时为 false；恢复条件满足后为 true |

若提升时仍有 `unverified` 资产，事件随提升状态保留，到所需完整快照恢复后才最终结算，包含等待恢复的时间，不在毫秒级提升时提前结束。测试分别复现 **5.1 秒、18.7 秒**旧源静默且合流 receipt 很新的条件，断言不会再报成几十毫秒。

`ws_takeover_gap_scope` 明示这一保守口径。合流实际交付另看 `ws_continuity.published` 的逐资产 `receipt_gap_ms / max_receipt_gap_ms / receipt_age_ms`，连续性日志另带 `merged_receipt_age_ms / merged_max_receipt_gap_ms`。无交换所序列号时，不能仅凭某个 receipt 很新承诺没有遗漏历史交易。

## 3. ingress_pressure：真实处理落后，不能靠放宽 ready 门槛解决

162 个采样中，未就绪备份的压力原因有 **113 次 queue_depth、113 次 queue_lag**，只有 1 次 TCP pending；以下是整个固定窗口的备份样本，而非仅 08:23 后的小时增量：

| 分片 / 组 | ingress_pressure 样本数 | 未就绪时最大队列深度 | 最大等待秒数 |
| --- | ---: | ---: | ---: |
| 0 / BTC 15m | 36 | 5383 | 11.231 |
| 1 / BTC 5m | 37 | 7630 | 12.784 |
| 2 / ETH 15m | 13 | 1082 | 4.288 |
| 3 / ETH 5m | 27 | 1933 | 5.225 |

这些等待已经超过 1 秒就绪标准，不能视为单组独占连接后必然没有压力，也不能通过提高队列深度门槛制造 ready。保持 snapshot、timestamp、resync、真实 queue-wait 等约束；增加 **`readiness_blockers`**，明确区分发布就绪与已有 `admission_pressure_reasons`（新增订阅准入）。当前盘口完整且已追上的备份，不因瞬时 TCP pending 而丧失 ready；真实排队仍否决 ready。

本轮从重复处理成本入手：

1. 完整盘口存在有效交易所 hash 时，以 **book 类型、资产、时间戳、hash** 计算共享指纹，避免为了比较副本再次序列化大量盘口档位；无 hash 时仍用完整内容指纹。交易打印的同源重复次数语义保留。
2. `owned_events()` 没有实际过滤 price-change 行时返回原不可变解析对象，保留共享指纹、减少反复构造字典。真正过滤时仍返回独立事件。
3. 缩小去重工作集，并为每条连接建立独立的接收字节预算，见下一节。

本机合成双路回放：10,000 个事件、20% 为 500 档且带 hash 的 book，另外为 delta；同一进程三轮比较 round12/13。CPU 时间分别为 round12 **1.0720 / 0.9964 / 0.9937 秒**，round13 **0.7162 / 0.6837 / 0.6784 秒**，中位约降 **31%**；两者均发布 10,000、去重 10,000。该微基准不包含真实网络、SQL 和全部生产竞争，不能据此保证生产零备份时间已改善。

## 4. 内存：复现缓存成本、补齐内层与字节上限

在本机用 `tracemalloc` 对原实现与新实现运行相同合成输入并 GC 后统计：

- 80,000 个不同事件后，旧 `FeedMerge.seen` 保留 65,536 项，追踪分配约 **25.06MiB**；新默认保留 16,384 项，约 **7.13MiB**。主要分配落在 seen 条目、来源计数字典、指纹对象及 OrderedDict 节点。
- 旧 seen 虽然限制键数，但每个值内的 `counts[source]` **没有来源数上限**。同一个冻结事件经不同连接代次反复出现时，合成测试得到 **20,000 个来源**；新实现最多 **4 个来源/键**。这是真实可复现的内层无界结构，不代表生产一小时实际产生了两万个代次。
- 接收 FIFO 原来只限 16,384 帧，没有字节预算；当帧包含大快照时，帧数有界不等于工作集足够小。新 `WireQueue` 默认每条连接 **16MiB charged bytes**，配置 `POLYMARKET_OBSERVER_WS_RECEIVE_QUEUE_BYTES`，与帧数约束同时生效。计费包括 tuple/receipt 余量及文本最坏存储宽度；这是队列原始帧预算，不是整进程 RSS 上限。

去重配置为 **`POLYMARKET_OBSERVER_WS_MERGE_CACHE_MAX`**，默认 16,384，允许 1,024–65,536；60 秒 TTL 保留。迁移合并缓存也遵守同一上限。顺便修复“缓存已满时更新现有键仍驱逐最旧键”，防止恰好驱逐正在比较的事件而漏掉跨副本去重。

FIFO 触及字节上限时，沿用已有 overflow → epoch/resync → 完整快照恢复协议，明确累计 drops，不静默截断盘口或假装 ready。取出与 discard 均同步减少字节计费。

新增/补充观测：

- 主路 `ws_receive_queues.*.charged_bytes / byte_limit`；备份 `queue_charged_bytes / queue_byte_limit`。
- `ws_merge_metrics.*.capacity / sources_per_entry_limit`，保留 entries、levels、evictions。
- `ws_book_memory`：盘口资产/档位、待写 recording 条数、交付采样条数、纸面历史事件条数；仅计数，不改纸面模型或历史计算。
- `ws_continuity.history_assets / history_entries` 与有界、随资产退订裁剪的 publication 账本。

**不能据本机试验断言生产 162→371MiB 的全部增长已经定位或消除。** 给定日志没有生产 tracemalloc，也没有这些结构的完整对象/字节时序；缓存工作集、真实 FIFO 积压与 Python allocator 保留都可能贡献 RSS。已消除可复现无界维度并收紧大结构预算，后续仍必须用新增计数与 RSS 对照，确认跨多个换期后基线是否稳定。

## 5. PostgreSQL 四连接池竞争

09:02:06 的原始告警为：**max=4、used=4、idle=0，等待连接**。它早于 09:02:33 主路故障约 27 秒；不能把它归因于后来的这次故障恢复。

代码路径核查：WS reader/worker、`SnapshotRecovery` 的 HTTP 修复与发布不直接借数据库连接；观察数据先入有界 WriteQueue，由单个 writer 批量提交。不存在每次 WS 恢复为每个资产另起 SQL writer 的实现。

真正的竞争来源是固定后台任务叠加：纸面账户持有一个长期 advisory-lock 租约，并另用连接轮询/保存；观察器 writer、状态/日计数、resolution 读取原先也可同时借连接，另有进程心跳。四槽池没有足够余量。日志未记录各连接的借用栈，不能确认那一刻四个持有者分别是谁。

新增 `observer_db.connection()`，将观察器、recording resolution、DailyStats 的 SQL 通过**共享单槽**串行准入。纸面账户及模型不改，数据库全局池也不改、不扩容。状态 JSON 在借连接前生成，缩短持有期。行情接收不等待这把 SQL 锁。

新增 `ws_observer_database`（管理器运行时发布）：`limit=1 / active / waiting / acquisitions / max_wait_seconds`。六线程阻塞并发测试验证底层同时借用峰值为 1，异常后释放并继续服务；故障切换测试禁止 worker 借库仍能连续发布。剩余风险是慢 SQL 会串行拖慢观察器写入/状态，需结合 writer lag 与队列深度观察，不能承诺整个进程永远不会耗尽池。

## 7. 风险与获授权部署后的观察指标

本轮没有部署，以下是后续验收建议：

1. **半死接管**：核对 `byte_silence` 的旧源 byte silence、备份最近行情、就绪约束及提升时间，正常情况下在阈值加 worker 调度延迟内提升。3–5 秒是判定阈值，不是网络/调度延迟的绝对 SLA。仍检查主路与备份都停收、换期静默、迟到旧回调，不能仅统计 promotions。
2. **真实连续性**：联合检查 `takeover_gap_ms / receipt_gap_ms / gap_final`、source silence、snapshot_restored、逐资产合流 receipt 间隔及数据库书写延迟。控制提升耗时单独看 `detection_to_takeover_ms` / `ws_failover_ms`。不再以 22ms 代替长源静默；合流 gap 与旧源 gap 分列，避免相反方向误判。市场自然静默也会增大 receipt 间隔，须核对同组备份是否同时有新行情。
3. **备份覆盖**：比较相近流量、多个完整 5m/15m 周期的 ready_ratio、zero-ready 累计/steady 分量、`readiness_blockers`、FIFO wait 与 CPU。真实 queue_wait >1 秒依然不可 ready。本机约 31% CPU 改善不能代替生产对照；若积压未改善，继续以队列/锁/CPU profiler 定位，不能只抬 ready 门槛。
4. **内存与恢复代价**：持续对照 RSS、seen entries/evictions、FIFO charged bytes、盘口/历史/continuity 计数。默认缩小去重缓存会缩短高流量下的有效去重跨度；超过容量/TTL 或四代来源之后的迟到副本，尤其交易打印，仍可能超出去重保证。字节上限可能更早触发 resync，必须观察 overflow、REST requests/throttled、恢复时间及零备份时长，不能用降 RSS 掩盖连续性退化。
5. **hash 假设**：快速比较依赖交易所 full-book hash 正确代表该资产与时间戳下的盘口。无 hash 仍走内容指纹；若上游出现同资产、同时间戳、同 hash 却内容冲突，需要保留冲突样本复核。未声称存在交易所连续序列保证。
6. **数据库**：观察 `ws_observer_database` 等待、writer_inflight、writer_lag_seconds、写队列/drop、pool exhausted 及健康状态。单槽为纸面账户和心跳留余量，慢 SQL 仍可能累积写入延迟；没有改变账户租约或全局数据库池。
7. **保留 round12 验收**：主路 1013、1008、整批本地关闭、冷门 delivery latency、四热门组隔离与 YES/NO 同片继续观察。PING 维持 10 秒，默认一条热备，PAPER_AUTO 保持关闭。
