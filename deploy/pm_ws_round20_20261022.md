## 实施、验证与风险

### P1：发现自愈

PublicClient 明确拒绝 3xx、非 JSON Content-Type、无效 JSON；只记异常类、状态码、目标 host、剥掉 query/userinfo 的 Location（不记响应正文/凭证）。连续两次失败关闭并重建连接池，最长 300s；成功清零失败数。无立即重试，不提高 REST 请求频率，不跟随重定向。缺失 series 不再永久缓存 None。DiscoveryHealth 只保留失败热门系列上轮仍未到 endDate 的市场；过期照常移除。四组 series 同时失败连续 >120s 写 discovery_health.level1_alert。

影响面：所有 Polymarket 公开 HTTP 读取；Session 轮换使首次请求重建 TLS，额外握手而非额外请求。旧目录保留不延长有效期。行为测试覆盖 301、HTML、JSONDecodeError、无额外请求、最大连接寿命、有效期及告警复位。P1 相关 111 项通过。

### P2：备份资格、选择与数量

已有 envelope 必须同时满足 PONG age ≤15s；首个 PONG 前只给打开后 10s 的启动宽限。liveness 仍不要求全量盘口，避免恢复早期“等不到 book 就一直不 ready”的缺陷；invalid/resync/delivery_gap/current subscription 等闸门保留。正常/强制恢复候选均核对 PONG；选择 ready 候选中 pending_wait 最少的，等队列时优先较新连接。只有自己的消费 worker 能晋升，并在 lifecycle lock 内再次核对选择。

主队列 ≥0.5s、比最好备份差 ≥0.25s，持续 1s 后记 ingress_pressure 并允许健康备份接替；晋升后 30s 不因该主动压力规则来回切换。断线/失效切换不受这个压力冷却阻挡。它处理“晋升后继续积压”的同一候选健康问题，但不能承诺在 CPU 再次饱和时也保证 1.5s，四核容量仍是前提。

默认每热门 shard 从 1 备提高到 2 备，明确配置可设 1–5；移除“一条 reserve 覆盖同键”的结构上限，逐条错开至少 10s 建额外副本，无覆盖组先建。实际生产配置有显式 1 时仍服从配置；此次不读部署环境文件。正常四个热门进程共增加 4 条连接，热门字节/解析从两份变三份（约 +50%）；不是把 status 中错误相加的 5 当成真实配置。上限未公布，不能保证不会碰到上游未公开限制；不部署。

换场调查：19:10 证据确认新场首帧晚 13.7s，代码中 current_subscription/missing_envelope 在新资产未到时会让备份不 ready；该次没有保留逐连接完整 envelope/订阅时序，无法单凭旧资料确认是哪一条阻塞。已有最近下一场、最后 90s、仅备份的预订阅保留；也保留高字节场次的压力锁存，避免流量增加和订阅抖动。新增 ws_rollover_preparation：future_assets、seen_future_assets、current_subscription_pending、prewarm_pressure_blocked，部署后可判明缺失 catalogue、预订阅被压力阻挡还是 envelope 未到。不用尚无证据的更激进预订阅掩盖根因。

追加根因证据（修改缓存预算前）：六来源依次提交同一成交，只有第一份应发布；随后主来源提交第二笔相同内容成交，旧 FeedMerge 却返回 False。ws_redundancy.py 的 unique/fanin hint、continuity 来源表均硬限 4；配置 1主+5备后会淘汰仍活跃来源的 multiplicity 计数。这个新预算的影响面必须一起处理：来源上限有界提高到 8（6 个活跃来源及少量旧代），不改变去重键、盘口顺序或实际连接数；加入六来源两笔相同成交只发布两笔的行为测试。

影响面：仅观察器冗余与诊断。不能保证刚晋升连接不再被上游踢；通过排除旧 PONG、比较积压和多副本减少暴露。行为测试包含 94s PONG 被拒、0.11s 备份优先、持续积压切换、配置 5 备可逐条达到且移除不泄漏。

### P3：读停滞分类与晋升事件

切换前读取内核 FIONREAD；RecvQ>0 或本地队列严重积压记 ingress_pressure；RecvQ=0 才能给 remote_silence_confirmed，平台不支持时明确为未确认。保留原健康备份接替能力，不因重命名暂停恢复。liveness 与 shadow 晋升共用 transfer_outage；每次晋升都建立/继承中断事件，无后续发布时保持 pending/None，不能填 0 冒充恢复。

影响面：故障分类、status、切换事件；不改盘口合并规则。物理静默 >20s、历史成交不确定性仍仅告警。行为测试以 700KB RecvQ 和 27s 未读取验证 ingress_pressure 及未完成缺口转移。

### P4：错峰退避与整体断开标识

原 full jitter 保留指数增大，但增加角色/热门组固定错位：热门主底座 0.2s + 组序×0.2s，冷门 1.2s + shard 序×0.2s，备份 2s + 组序×0.2s；再叠加指数随机部分，最多 30s。不再将备份失败退避截成 2s，也不让 pong_dead 绕过退避。首帧立即订阅、10s PING 和后续订阅 pacer 保持。

各子进程保留有界远端关闭事件；父进程合并去重，1s 内至少 4 条、覆盖至少 2 组的无关闭码断开写 ws_server_disconnects，分类 server_wide_disconnect_suspected，明确 cause_confirmed=false。不能仅由时间相关性宣称证明服务端故障。

影响面：重连/补备时间。热门当前仍有主时，补备会多等数秒，换取降低同时重建被再踢风险；主断有 ready 备份时，晋升无需等待重连退避。行为测试覆盖角色优先、组错位、指数封顶、14 条跨进程关闭只记一簇。

### P5：统一口径

唯一业务缺口定义位于 ws_redundancy.BUSINESS_GAP_DEFINITION：同一中断事件、同一资产从中断前最后一次合流发布，到中断后第一次合流发布；取受影响资产最大值。用发布时刻，不用 socket 读入时刻或检测到晋升耗时。watch_gap 固定锚点，publication 闭合一次；主故障、continuity 事件、双踢共用。没有基线写 unmeasured_no_baseline，不能宣称 0；有 gap_maximum.asset/at，完成由 merged_gap_final 标记。

原 ws_continuity.merged_gap_ms 移除，改为 receive_cadence_ms.hot/cold，60s 时间窗口、1s 桶、固定直方图。热门为接收间隔，冷门为 max(0, 接收间隔−交易所时间间隔)；它是节奏诊断，绝不是验收字段。跨进程合并 histogram 后重算分位数（上界桶估计），保留真实最大值的资产与 UTC。不再取各进程 p95 最大值。

双踢配对从 1s 延到 15s，按物理 source 去重，包括备份晋升后再被踢。只有供给确实中断且事件闭合的配对计 business_gap；仍有其他健康供给时仅告警。验收读取 ws_hot_primary_failures.<group>.events[].merged_gap_ms（final=true）≤1500，双踢业务缺口每 UTC 小时 ≤1；ws_acceptance_gap_scope 写明路径。仍需同时检查 pending/unmeasured，不能把它们当通过。

zero_ready_backup_active 改为“该组进入覆盖计量且当前 ready 数=0”；父进程按所属热门进程选择 coverage，不再把 inactive 的布尔值和配置目标相加；shard/reserve 键正确重映射。ready 后远端关闭单列 ws_backup_wire_failures；准备阶段失败仍计 ws_rotation_failures，避免将已有健康备份寿终误报成准备失败。

影响面：status 消费方必须迁移旧字段；直方图 p95 是桶上界，最大值为精确值。每秒桶内计数避免逐发布保留样本，窗口不再受流量/4096条限制。行为测试覆盖共享事件 2000ms、后续发布不改值、300s 冷门自然静默扣除、100 个 1ms 加一个 1000ms 合并 p95=1ms、7s 双踢、owner coverage 和多 reserve 键。

### P6：回放正确性调查

受控实验给同一 producer 每帧增加 0.5ms 调度迟滞，四核、5688/s、8s 计划（不连接线上）：旧脚本到固定时间即取 SHA，valid=false；仅用原本的 QD_REPLAY_FULL_DRAIN=1 等完，同一旧盘口代码 SHA 恢复一致。新完成屏障也一致。原始结果在 deploy/r20/p6-controlled.jsonl。这个反例证明“队列接近零但 producer 尚未发完”足以产生历史症状；进一步按原始合成规则重建历史 SHA：其他三组取完整计划、BTC5m 仅到 seq=63144，即精确得到历史实际 SHA e53fa296…；完整 BTC5m 应到 seq=76562（计划 76563 条），尾部 13418 条尚未体现在父盘口。完整重建同样精确得到历史 expected b3b579c7…（p6-historical-prefix.json）。这证明历史结果是正确流的未完成前缀，并非一个任意错误的盘口；原记录未留 producer/IPC 最终序号，不能事后定位是在生成、IPC 发送还是父消费层未排空。完成判据缺失则是确定的回放缺陷。

实现先等待 producer 结束，再等待 active FIFO unfinished_tasks=0 和 snapshot hold 释放，再用最终 outbox seq 等父进程实际消费。urgent drained 可以先到，但 seq 未消费不能通过。超时 valid=false，输出 drain_complete 和 mismatch_assets。ReceiveQueue discard/consumer 正确维护任务完成数。离线假 socket 补齐与真实 transport 一样的备份独立 PING/PONG，否则新 PONG 闸门会揭示旧回放假 socket 10s 后无心跳的夹具错误。

影响面：回放完成协议、队列记账；未修改真实盘口应用/去重算法。行为测试覆盖慢 producer、已出队仍处理中的消息、discard 不误清 in-flight、urgent ack 先到、备份独立心跳。历史问题证据不足以断言线上盘口绝无丢失；完成屏障、SHA、IPC drop/epoch 与队列指标要一起检查。

### P7：只调查，等待 roc 审批

四核后资料支持“上游单连接发送/缓冲路径是候选瓶颈”：同机 CPU 等待下降、RecvQ/qw 基本 0，仍集中 BTC5m 5–6 次 1013/h，约 940 帧/s、1–2MB/s（约 8–16Mbit/s）。单秒/20s TCP 采样不能排除毫秒突发、网络调度或上游共享缓冲，因此不是已证明的发送上限。官方文件第 5 节提到其他语言、单连接且本地无积压的相似报告，增强上游假设，但不是官方确认。

假设两个 token 字节均衡且服务器严格按 token 过滤，拆分可把每条链路平均载荷降至约 470 帧/s、0.5–1MB/s；这是最好情形估计，不是实测收益，原始数据没有逐 token 字节归因。若某 token/共享 book 突发占主导，收益可能远小于一半，甚至不能改善共享缓冲问题。总字节基本不降，握手、PING/PONG、TLS、断线恢复和订阅状态翻倍。

以新默认 BTC 主+2备为例：BTC 从 3 条增至 6 条（两个 token 各主+2备），全观察器再加 3 条；若仍主+1备则该组 2→4。官方市场频道 token 无上限，IP 连接/握手/发送缓冲上限未公开，不能给“确定未超限”的保证。每 token 仍须保留 fresh PONG、独立 snapshot/epoch 和 group 覆盖；组 ready 必须两个 shard 都有备，不能相加掩盖半边失效。建议批准后先记录逐 token 字节/最大 100ms burst，再做观察器 A/B，评价每小时业务缺口与 ready 覆盖，而非只看 1013 数量。本轮未实现拆分、未探测/连接生产 WS、未绕过地区限制。

### 部署后观察项（本轮不部署）

- ws_hot_primary_failures 各事件的 merged_gap_ms/final/business_event_id、gap_measurement、gap_maximum；任一已完成业务缺口 >1500ms 不通过；pending/unmeasured 必须单列，不能算零。

- 1008 必须为0；偶发1013单独观察，不把它自动当验收失败。核对每条关闭的 source、物理角色、PONG age、100ms burst、RecvQ、queue_wait。
- 每组 ready_backup_count/target_backup_count 与 ws_child_ready 一致、zero_ready_backup_active 真实为零备；PONG age 超15s不晋升。记录补备退避期间零备秒及新默认2备的 CPU/带宽，不能因多副本重新把四核打满。
- ws_rollover_preparation 在换场前90s和换场后：目录是否有下场、压力锁存是否阻止预订阅、future_assets 是否有 envelope、当前订阅是否仍 pending。19:10 的单一阻塞项尚需这些字段提供最终证据。
- ws_server_disconnects 的跨组整体关闭簇、重连实际错峰、连续失败退避；不是仅凭簇标记就断言上游原因已证实。
- discovery_health.level1_alert（四热门组失败>120s）、retained_markets、HTTP 异常类/状态/host/Location，确认 Session 轮换后能自愈、过期市场仍退出。
