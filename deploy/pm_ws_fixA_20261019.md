## 0. 结论先说

- **A 做到了它该做的**：supervisor 持 lifecycle_lock 时间 −87%，tick CPU −81%，`ws_recovery.metrics()` 每次 1.9–4.2ms → 0.005ms，Pipeline.metrics 持 _PIPELINE.lock 最长 5–8ms → 0.2–0.4ms；进程 CPU −1.5%～−5%（无剖析器），剖析下 −9%。
- **回放门槛：未全部通过。** 负载 ≤3300 物理帧/s（本机约 0.75 核）时没有任何指标变差（差异在 50ms 采样粒度内）。**接近饱和（3800 帧/s，约 0.86 核）时，备份变好、主路变差**：备份就绪率 0.95→1.00、备份排队 p99 727→424ms、resync 减少；但主路排队 p50 7→151ms、p99 501→603ms，合流发布延迟 p50 220→366ms，p99 第二批 0.97→1.15s。
- 原因（有数据支持的解释）：r17 里 supervisor 每 0.2s 长时间持 lifecycle_lock，**等于意外地给备份限了流**；A 去掉这把“刹车”后，省下的 CPU 和原本卡在锁上的时间被备份用掉了。在单核饱和下这又是零和——正是根因报告第 6 节描述的模式。A 省下的 CPU（几个百分点）不足以抵消这次重新分配。
- **建议：不要单独把 A 部署到生产**（生产比 3800 更饱和，主路排队大概率上升）。A 作为 B（每热门组独立进程）的前置一起上线，或在 A 之上加“主路优先”的明确调度（属于 B/C 范围，本轮没做）。是否部署由 roc 决定。

## 2. 改了什么

| 文件 | 改动 | 语义 |
|---|---|---|
| `ws_recovery.py` | 新增 `hour_totals`：计数时加、桶过期时减；`metrics()` 直接读，不再 `sum(self.hour.values(), Counter())` | 输出与全量重算逐项相等（随机 9000 步 + 过期测试） |
| `observer.py` `MarketConnections.tick` | `_tick()` 只做控制；STATUS 构建拆到 `publish_status()`。supervisor 用 `tick(status=False)`，只有 STATUS 超过 1s 未更新才重建；市场循环和测试显式 `tick()` 仍每次重建 | 恢复/轮换/速率/零备份积分仍每 0.2s 执行；STATUS 最多 ~1s 旧（落库本来就 10s 一次） |
| `observer.py` `Pipeline.metrics` | 锁内只拷贝 books 键、metadata、delivery_samples；排序/分位数在锁外 | 输出相同（测试比对） |
| `observer.py` `Pipeline.receive` | 每次发布只读一次墙钟，`lag_seconds`、发布延迟、`last_message_at` 共用 | 热路径少一次 `datetime.now()` |
| `recording.py` | delivery 样本多存一个“交易所时间→合流发布”延迟；新增 `publish_p50/p95/max_ms`、`publish_latency_p95_ms`、`ws_delivery_latency_scope` | **原 `p95_ms` / `delivery_latency_p95_ms` 含义不变**（交易所→socket 收到），新字段包含应用队列等待 |
| `tests/test_install_script.py` | 子进程环境固定 `HOME` 和 `QUANTDINGER_INSTALL_DIR` 到 tmp | 修 flake：`install.sh` 在 `set -u` 下读 `$HOME`，无 HOME 的运行器会失败，有 HOME 时又依赖真实家目录。没改 install.sh |
| `scripts/polymarket_ws_worker_replay.py` | 新增可选参数：`--lock-timing`、`--market-loop`、`--rest-hour-buckets`、`--prod-gil`、`--gil-load`；新增输出：主/备排队采样、合流发布延迟、RSS、锁等待/持有统计 | 默认参数下行为与原脚本一致 |
| `tests/test_polymarket_ws_fix_a.py` | 9 项新测试 | — |

**没动**：故障接管、合流/去重、REST 恢复、心跳、关闭码处理、就绪判定、策略、PAPER_AUTO、交易闸门。

关于“把 STATUS 构建完全移出 lifecycle_lock”：测了以后**没有这样做**。限频后单次构建约 1.1ms、≤1 次/s（锁占用约 0.1%），而移到锁外要在别的线程改 `states/backups` 字典时遍历它们，会有 “dictionary changed size” 一类竞态。收益可以忽略，风险是新的，所以留在锁内。_PIPELINE.lock 那边的统计（Pipeline.metrics）已经完全移出。

## 3. 影响范围（blast radius）

- 监控字段：用同一个场景对比两份代码的 `snapshot()`，**516 个键路径一个没少**，新增 13 个（`status_key_diff.json`）。p35/p51 脚本读的字段（`ws_backups`、`ws_receive_queues`、`ws_rest_recovery`、`ws_hot_backup_by_group`、`ws_delivery_latency_by_activity`、`ws_process_cpu_cores` 等）都在。
- 行为变化（只在观测层）：
  1. STATUS 刷新从约 6 次/s 变成约 1 次/s（市场循环 1 次/s + supervisor 兜底）。
  2. `ws_process_cpu_cores` 的窗口从“上次 tick 起约 0.2s”变成“上次构建起约 1s”，更平稳，含义不变。
  3. `ws_tick_gap_seconds` 取最近一次控制 tick 的值，含义不变。
- 性能变化：见第 0 节，饱和时 CPU 会从主路往备份方向重新分配。**这是本 PR 最大的风险**。
- 内存：delivery 样本每条多一个 float，上限 8192 条，最多约 +0.3MB，有界。

## 5. RSS 观察（生产约 +27MB/h）

- A 碰过的结构都有上限：REST 小时桶 ≤3600（`hour_totals` 键 ≤18）；delivery 样本 deque 8192；`primary_failures` 按热门组（≤4）各 64 条；`observed_hot_groups` 只收 HOT_SERIES；STATUS 里按连接的字段每次整体替换，旧连接不会残留；`metrics_view` 是临时拷贝。
- 120s 浸泡（2800/s）：base RSS +31.8MB，fixA +31.7MB，一样。20s 回放各负载下两版增长也一样（50–60MB）。这部分是历史缓存（16MiB 上限）、队列、解析缓存在填满，不是 A 引起的。
- 结论：A 范围内没有发现无界增长，也没改。生产的持续增长要另做：堆采样（tracemalloc/py-spy dump）对比 1h 前后，重点看退休连接（`retiring` 里线程不退出时保留的 state/shadow）、`ParsedFrames`、continuity history、按 asset 的字典在换期后有没有清掉。
