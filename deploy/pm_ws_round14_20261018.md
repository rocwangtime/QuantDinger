## 1. 主备同时 1013：错相与成对流量诊断

10:35:45 的 BTC5m 主路关闭时有就绪备份，控制切换约 10.51ms，保守 receipt gap 为 981.572ms。10:46:38 的主备故障证据日志相隔约 327ms，连接年龄分别约 **1416 秒、653 秒**，并非同时到达某个固定连接寿命；当时无就绪备份，最终依赖 REST，gap 为 **1332.446ms**。

两条连接是不同 TCP 连接、不同本地端口和 `cf-ray`，均经过 SIN。双断前主路 TCP pending 为 0、接收窗口约 1.20MB；备份 pending 为 0、窗口约 356KB，PONG 正常。没有看到 TCP 接收窗口归零或长时间断字节，不能据这些证据认定是客户端 TCP 背压导致上游拒绝。

流量叠加需要区分两件事：它确实增加本机处理负担，但未证实存在上游的固定合计带宽限制。双断证据中的最后一分钟主备分别收到 18,723,007 / 19,060,233 bytes，合计约 **0.63MB/s**；未关闭的 10:44:14 样本主备速率合计约 **1.81MB/s**。采样时间尺度不同，且没有交换所内部队列证据，因此这只能反驳简单的固定阈值解释，不能排除同步行情突发或共享上游故障。

改动：

- 首次热备建连相对主路随机延后 **7–11 秒**。配置 `POLYMARKET_OBSERVER_WS_HOT_BACKUP_STAGGER_SECONDS` 默认 7，并增加最多 4 秒抖动；0 可关闭。已经保护过的主路及提升后的备份沿用立即补副本逻辑，不重复等待启动错相。
- 备份初始订阅把当前资产顺序反转；当前资产仍优先于下一场预热资产。首个 market 订阅仍在 on_open 立即发送，后续批次继续使用既有共享准入，避免破坏 round13 的 1008 修复。
- 备份首个文本心跳在 3–5 秒，主路首个在 10 秒；随后均维持 **10 秒周期**，且首个订阅成功前不发 PING。
- 关闭证据增加 `pair_load`：对端连接数、合计接收速率、合计 60 秒读字节、对端 queue wait、心跳初始相位，便于下一次核对相关关闭。

默认仍为每热门分片一条备份，没有增加流量副本、使用新端点、使用凭证或假设未经证实的分片接口。错相降低相关风险，不能保证同一公开上游的两个连接永不同时失败；已有年龄差 763 秒的反例也说明不能只靠年龄错开承诺零缺口。

## 2. catchup 与 queue_wait：真实处理积压及共享锁成本

`catchup` 的 53 个样本大多与 `queue_wait` 的 50 个样本重合。它是 `state.ready=False` 的派生标签，并非证实存在永远等待两资产时间戳相等的 barrier；当前热备逻辑本就没有那个全资产等时条件。

生产存在真实积压，而且主路汇总的 dropped=0 掩盖不了备份丢帧：

| BTC5m 备份样本 | queue wait | 累计 drops |
| --- | ---: | ---: |
| 10:43:11 | 9.678 秒 | 0 |
| 10:43:42 | 9.945 秒 | 16,393 |
| 10:44:14 | 5.091 秒 | 32,778 |

关闭前备份已发生两次 overflow/resync；约 1.41 秒等待使它正确地无法接管。FIFO 未处理完、丢帧后恢复、共享锁竞争都是真实成本，不能抬高 1 秒门槛制造 95% ready。

代码核查和本机 profiler 确认以下重复成本：共享 parser 原先持锁完成大 JSON 解码；连续性账本和合流分别生成每行事件身份；主路、私有备份盘口、纸面历史重复构建完整盘口映射；备份还在全局 lifecycle/Pipeline 锁内构建私有盘口。

本轮将 JSON 解码、指纹/事件身份准备移到全局发布锁之外，连续性与合流复用同一事件身份。完整盘口映射在不可变解析对象上只构建一次，三个可变消费者各自复制，避免共享可变盘口；解析缓存的字节预算也计入新增映射。

备份私有盘口在自己的锁内构建，然后才进入全局发布。发布前重验 inbox、epoch、shadow 身份、资产和订阅 activation；重订阅跨过分离处理时触发 resync，旧 epoch 不得进入新盘口。REST/监督器仍不能越过备份 worker 提升，保留已有防止遗留已弹出 delta 的协议。

就绪检查进一步使用 **队首及正在处理帧的实时年龄**，避免拿上次出队时的低等待值冒充当前已追上。队列彻底排空后清除历史等待值。snapshot、timestamp、resync、delivery gap、当前订阅及修复约束全部保留，真实等待 >1 秒仍不可 ready。

同一进程、相同 6000 帧输入的三轮合成双路回放，含 20% 双资产大快照及多行 delta：round13 CPU 为 **3.2980 / 3.2013 / 3.1190 秒**，round14 为 **3.0466 / 3.0253 / 2.9695 秒**，中位约降低 **5.5%**；每轮均发布 6000 帧、去重 98,400 项。全局锁内工作减少比总 CPU 改善更明显，但没有生产 profiler，不能把生产每段排队精确归因于某一函数。

新增四热门组分别进行已热身短回放，断言 ready ratio ≥95%、无 overflow/resync、1013 后 <1 秒提升且共享盘口保持。该回归覆盖本地行为，未模拟上游同时关闭两路，也没有证明生产负载下的 95% SLA。

## 3. history_events：有界大对象高水位，补全字节与静默淘汰

原 `BookHistory` **已经**每资产限制 2000 条、10 秒，因此不能把 9.8k→16.5k 直接定性为无界事件数泄漏。窗口末尾它又降至约 11.5k；盘口档位约 3500 保持稳定。问题是事件可携带完整盘口，条数不代表内存，而且时间淘汰仅在该资产再收到事件时执行，静默资产能长期保留旧历史。Python allocator 也可能保留曾分配的高水位。

本机 `tracemalloc`：同一资产连续 2000 个、每个 400 档快照，旧实现保留 2000 条，追踪分配约 **94.53MiB**；新实现保留 140 条加时间戳锚点，追踪分配约 **6.69MiB**，计费约 **15.89MiB**。这复现了旧实现的高内存工作集，不能证明生产 RSS 增长的每个字节都来自 history。

新增整个历史缓存共享的 **16MiB 计费上限**，同时计入历史事件与已折叠 base；原每资产条数和时间配置不改。触及预算时按最老事件折入 timestamped base，早于 base 的查询返回 None，不能编造被淘汰的历史；单个锚点仍超预算则淘汰该资产历史。增量、删除价位、交易所时间都保留。观察器 evaluator 即使没有新行情，也定期淘汰超过 10 秒的静默资产；退订/重连统一使用预算感知的 forget/retain。

`ws_book_memory` 增加 `history_charged_bytes / history_byte_limit / history_byte_evictions / history_idle_evictions`。计费是缓存预算，**不是进程 RSS 的硬上限**；临时对象、纸面查询副本、其他缓存和 allocator 仍需观察。

## 4. 10:43:42 的 book_age 10.1 秒

该样本 hot book_age p95 为 **10058.786ms**，receipt age p95 为 **9975.282ms**，原始 book arrival lag p95 只有 **83.504ms**；热门交付延迟 p95 约 143.726ms，调度延迟约 11ms。它主要是已发布盘口更新变老，不能解释为行情经过公网传输了 10 秒，也不是 10:46 的 1013 导致的。

同一时刻 BTC5m 备份排队 9.945 秒，仍持续收到约 413KB/s，支持应用处理/发布落后这一方向；字节一直在进，所以 byte_silence 不触发符合其定义。窗口没有保存逐 token 的 oldest 明细及主路逐帧队列剖析，**无法确定该最大值对应哪个 token，也不能排除该 token 自然静默**，不能把备份 queue wait 当作已证明的主路延迟。

本轮通过缩短共享发布锁工作处理已确认的成本，并新增实时未处理帧年龄约束；补测试重现“10 秒 age、约 83ms 到达延迟”仍被区分的口径。没有单凭 book_age 强制重连或放宽纸面 freshness。下一次必须保存 `book_hot_oldest_tokens`，与逐连接队列、合流 publication receipt 一起判断。

## 7. 风险和获授权部署后的观察指标

1. **备份覆盖率**：至少观察多个完整换期、每组 30 分钟以上的窗口增量。四热门各自 ready ratio ≥95%，同时检查启动/换期/steady 分母及 zero-ready 秒数，不用瞬时 ready 样本替代累计覆盖。队首/处理中帧真实等待 >1 秒仍必须不就绪；检查备份 drops、overflow、resync，不能只看主路汇总 dropped。
2. **切换连续性**：被踢时 ready_backup_at_kick、recovery=backup、worker 提升 <1 秒；联合检查合流 publication 的 receipt 间隔/年龄和实际盘口是否保留。旧物理源的保守 takeover_gap、gap_final 继续如实保留，不能用控制切换毫秒数代替行情连续性，也不宣称历史交易完整恢复。
3. **相关关闭**：核对主备端口、连接年龄差、心跳相位、订阅批次及 pair_load，统计 1 秒内双 1013。首次保护额外等待 7–11 秒；同源双路仍可能一起失败，届时 REST 不是零缺口保证。没有增加第三条副本来掩盖问题。
4. **热门 age**：保存 book_hot_oldest_tokens、receipt age、arrival lag、每路 FIFO/处理中帧年龄和合流 published 明细。若 receipt 旧但仍持续收流，优先取处理/锁 profiler；若两路该资产均静默，单独标记自然静默，避免混淆为网络延迟。
5. **内存与纸面证据**：history_charged_bytes ≤16MiB；静默历史随 evaluator 过期。对照 RSS、seen、FIFO 字节和历史计数，至少跨多个换期确认暖机后是否平台化。字节预算可能缩短高流量时的可查询历史，预算前的查询会拒绝，需观察纸面 lookup 缺失/跳过信号，不能为维持成交数恢复过期证据。
6. **线程与吞吐**：观察 queue wait、process/lifecycle wait、CPU、冷门 delivery p95，确认移出共享锁后的收益；分离处理依赖 epoch/订阅校验，若新增 resync 必须分析原因。解析缓存多计入映射后可能更早淘汰，CPU 微基准改善不代表所有生产负载均改善。
7. **选市场与原验收**：active cells 必须属于当前记录和发现范围，检查 scope warning 和 selection 审计；已有有效风险/市场条件仍可拒绝纸面报价。继续保持 1008=0、冷门交付延迟不退化、DB pool exhausted=0、四热门 YES/NO 同片；PAPER_AUTO 保持关闭。本报告不授权部署。
