基线为长期分支 `fix/pm-ws-stability@3bbfd9f`。接续机器重启前的 observer、recording、ws_balance、ws_subscriptions 和新增 ws_redundancy 改动，在原工作区继续；未 reset、stash 或丢弃。仅修改公共行情观察器及其回归测试、独立诊断脚本和报告。未涉及钱包、签名、真实下单、CLOB 凭证、maker 参数、PAPER_AUTO、生产配置或服务依赖；未部署、未合并 main。

## 首先修复的 3 个失败

1. 冷启动测试沿用了“备用首帧等待全局额度”的旧断言；改为验证所有新连接均立即发送初始订阅，小分片一帧发完，不消耗后续批次的共享额度。
2. 字节容量加入后 `capacity_cost` 返回三元组 `(资产超额, msg/s 超额, bytes/s 超额)`；同步不可拆热组的回归断言，保留新增字节维度。
3. 订阅刷新取消旧 shadow 后，同一个 tick 又因旧连接年龄过大建立新 shadow。刷新取消增加 30 秒恢复窗口，不计准备失败，验证保留原连接和已有盘口、拒绝旧 shadow 的迟到回调。

这一步的 admission/rotation 测试为 **48 passed**。

## 行为与配置

所有下表配置使用 `POLYMARKET_OBSERVER_WS_` 前缀；本轮没有修改生产环境变量。

| 配置 / 行为 | 默认值 | 说明 |
| --- | --- | --- |
| `SUBSCRIBE_INITIAL_ASSETS` | 12 | `on_open` 同步发送首条 `type: market`；不等待全局限速或暂时流量压力。失效/退场连接除外。默认小分片全部资产一次发完；大分片先发 12 个。 |
| 后续订阅 | 2 资产 / 批、至少 0.5 秒、全局 4 资产/秒 | 使用等待队列轮询；跳过受压连接，避免按 shard-id 服务导致饥饿。首帧成功后才开放独立心跳；初始订阅之前也不发送退订。 |
| `HOT_BACKUP_SHARDS` | 2 | 最热分片各增加一条订阅相同公开资产的连接；0 可关闭冗余。保留已建立的备份直到故障或分配变化。 |
| 主备错峰 | 每代随机 90–120 秒 | 以主连接 `opened_at` 为基准，达到随机门槛后才准备备份。接管后新备份重新等待。若直到更晚才识别为热分片，实际间隔可大于 120 秒；握手、监督器调度也会增加延迟。 |
| `HOT_ROTATE_SECONDS` | **0，关闭** | 非零显式启用热分片按年龄主动轮换，例如 150 秒；就绪备份优先接管。数据塌陷故障检测仍保留，不属于热分片年龄轮换。普通分片仍沿用 2100 秒年龄轮换。 |
| `ROTATE_BUSY_WARM_SECONDS` | 3 秒 | 热/达到资产容量的备用连接缩短无压力观察期，仍须订阅完成、有完整快照、真实传输有新鲜 PONG、交付延迟不超过 1 秒。普通备用仍为 30 秒。准备总超时仍为 90 秒。 |
| 准备失败退避 | 60、120、240、480 秒封顶 | 原连接继续发布；记录 connect、subscribe、snapshots、ingress_pressure、pong_or_warmup 或 catchup_or_publication 阶段。成功清零连续失败。刷新取消和正常 1001 不计失败。 |
| 普通重连 full jitter | `uniform(0, min(30, 0.5 * 2**n))` | 首次重试上界 0.5 秒，之后指数增长、30 秒封顶。连接存活至少 60 秒后重置失败级别；1001 使用首次 jitter，不再同步立即重连。初次建立连接仍立即进行。 |
| `MAX_BYTES_PER_S` | 262144 | 与 12 资产、300 msg/s 一起进入容量规划；字节 EWMA 按原始帧大小分摊到资产组。不可拆组的超额如实报告。 |
| `HOT_SHARD_MSG_PER_S` / `HOT_SHARD_BYTES_PER_S` | 300 / 262144 | 消息或字节任一达到门槛即可识别热分片；排序同时考虑规划负载。 |

冗余由同一个 Pipeline 锁串行合流：跨来源按资产、事件内容、timestamp/hash 去重；同来源相同成交的重复次数保留，避免把两个实际相同成交合成一个。缓存最多 65536 个事件、保留约 60 秒；价位时间戳缓存也有 65536 上限。旧快照和旧价位不能覆盖较新时间戳；迟到成交仍可记录。shadow 自身也拒绝旧快照覆盖新状态，避免“元数据新、盘口旧”。

热备份不再等待所有资产同时追平不断前进的主连接时间戳；每个事件独立检查新旧。接管保留已经合流的有效盘口，只为缺失资产补 shadow 快照；缺失盘口的补齐必须达到保留的主流水位。主连接失败时，如果备份已就绪，不清空已经合流的盘口；仍在预热的备份获得有界准备窗口，避免同时建立第三条近乎同龄的连接。旧代回调不能清除新代盘口。资产分配变化取消对应准备状态，清理合流缓存。

1008 单独统计为 `invalid_subscription`，1001 为 `server_shutdown`；1001 不增加 slow consumer 或轮换失败计数，也不调用异常处理。兼容 websocket-client 1.9.0 的 ABNF 错误和较新版本的 `status_code/reason` 错误对象；重建环境的真实 loopback WS 测试发现并补上了这项兼容性。

关闭诊断同时覆盖 error→close 和仅 close 路径：reason 文本、连接存活时间、关闭前约 60 秒读取字节、原有有界 TCP/心跳/调度历史。字节以解密后的 WS 传输读取计数，采用 1 秒桶，窗口边缘有小于 1 秒的分辨率误差，不是加密 TCP 字节。握手时保存并在断开后保留 `cf-ray`、`server`、`date`、`sec-websocket-extensions` 四个白名单响应头；不记录 Cookie、Authorization 或其他任意头。每连接每秒平均字节峰值进入 `ws_receive_queues[*].peak_receive_bytes_per_second`，不是亚秒峰值。

## 官方资料核对、压缩与新鲜度结论

已完整阅读用户提供的官方限制调研，并核对 [市场实时数据](https://docs.polymarket.com/market-data/realtime-data)、[Market WS 规范](https://docs.polymarket.com/api-reference/wss/market) 和 [官方仓库 issue #122](https://github.com/Polymarket/rs-clob-client-v2/issues/122)。公开市场流无需鉴权；保持默认订阅字段，不开启增加流量的 custom features。没有文档化的按事件类型关闭 book 推送选项，`level` 含义也未说明，因此未猜测或改变它；`initial_dump: false` 只影响订阅初始快照，不能据此消除之后的成交快照。PolyBolt 不是本轮替代方案，也没有使用它的凭证。

新增独立脚本 [`scripts/pm_ws_compression_probe.py`](../scripts/pm_ws_compression_probe.py)，标准库实现一次 TLS/WebSocket 握手、请求 `permessage-deflate`，随后第一条 WS 消息订阅一个公开资产，再发送正常关闭。不解码行情、不重试、不读取环境或配置、不鉴权、不被生产代码引用。手动命令：

```sh
python3 scripts/pm_ws_compression_probe.py --asset-id PUBLIC_NUMERIC_TOKEN_ID
```

输出仅包含是否接受压缩和白名单响应头；已测试接受/不接受两种协商和首帧顺序。本轮**没有在生产或真实 Polymarket WS 运行探测**，因此服务器是否接受压缩仍未知，没有把压缩引入生产客户端。

p37 的 23 个两分钟离散采样中，hot p95 两次为 **3088.894ms（14:35 SGT）**、**5014.649ms（14:55 SGT）**。两次均不与已记录的 1013 关闭同刻；14:35 也没有年龄轮换，14:55 在 14:50–14:52 轮换之后。日志没有逐资产的 exchange/receipt 时间，不能把这些尖峰归因于本地排队、上游延迟或某个热组中的安静资产；不能声称已经修复这两个历史尖峰。新增 `book_hot_oldest_tokens`（最多 8 个）列出 token、group、group msg/s、book age、receipt age 和 arrival lag，结合 FIFO 等待及 Pipeline 锁等待区分这几类原因。hot p95 仍为订阅资产横截面统计，不是消息加权延迟。

## 仍未解决的问题与部署后观察

- **1013 仍是上游已知、未解决现象。** issue #122 是社区证据，不是维护者确认的根因；本轮没有线上 A/B，不能宣称它已消失。目标是备份可用、接管无可观测数据缺口和冷门资产新鲜度达标。
- 市场流没有全局序号；同毫秒不同状态的先后、超过去重窗口/容量后的迟到副本，不能保证严格 exactly-once。初次 90–120 秒错峰期间、备份尚未就绪或主备共同故障仍存在单路/无路窗口；冗余不是无条件不丢任何历史事件的证明。
- 两条同资产连接增加网络和 CPU，可能共同受上游/IP问题影响。0.5 秒 jitter 是上界，随机结果可接近 0；轮换准备失败另用分钟级退避。
- 12 资产/300 msg/s/256 KiB/s 是本地规划预算，不是官方硬限制。不可拆热组仍可超额，普通规划也不能消除单资产流量突发。

后续另行授权部署后，至少覆盖冷启动、多个完整五分钟周期和多次 1013；观察：

1. 1008 是否归零、首帧是否立即发出、各片待订阅数能否公平排空，首次 PING 始终晚于订阅。
2. `ws_backups` 的 ready、age、primary_age_offset_seconds、stage 和 pending；主备应有目标错峰；`ws_backup_promotions`、`ws_merge_metrics` 的 duplicates/stale/evictions；接管时盘口缺失、过期和成交记录是否出现异常。
3. `close_reason_counts.server_shutdown` 单独走势，`invalid_subscription`、slow consumer、重连延迟；1013 证据中的 reason、age、read_bytes_60s、cf-ray，以及 TCP pending、PONG 和调度延迟。
4. 每片 EWMA bytes/s、msg/s、资产数、三维 `ws_capacity_excess`、每秒字节峰值；增加冗余后的网络、CPU、FIFO深度/丢弃/交付缺口和 Pipeline 锁等待。
5. 冷/热资产 p95 和 `book_hot_oldest_tokens` 三种 age/lag，尤其五分钟换期；准备超时/失败阶段及退避；确认热年龄轮换默认仍为 0。是否开启非零值需要后续 A/B 证据。
