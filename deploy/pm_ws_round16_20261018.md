## 2. REST 恢复余量

`ws_recovery.py` 改为四个独占 HTTP 会话槽位，空闲会话复用连接；请求体、目标 URL 和 token 集合提前准备，资产变化时替换模板。只使用公开 `/books`，`trust_env=false`，PreparedRequest 不携带鉴权或 Cookie，不跟随重定向。保留连接/读取超时 `(0.4, 1)` 秒、响应大小、资产身份、盘口结构和 ±2 秒时间检查。

热门两 token 在有两个空闲槽位时并行拉取，各自校验、各自发布；慢 token 或单腿失败不会阻塞另一腿。槽位不足但仍有一个时退回批量请求。总并发始终不超过四个 HTTP 请求，没有无界任务队列。响应继续经过代次、epoch、所有权和合流水位检查，晚到响应不能覆盖更新的 WS 盘口。

断开且无就绪备份时，先启动 HTTP，再等待 Pipeline 锁进行故障记账和盘口清理；HTTP 与这些串行工作重叠。发布端仍受生命周期锁保护，不能抢在清理之前把响应发布后又被清空。

新增两种断开前准备，默认生效：

1. 热门主连接首次约 15 秒后、此后约每 15 秒做会话预热；双 token 并行预热两个会话，响应不发布、不缓存为将来的恢复数据。每次恢复都重新请求快照。
2. BTC5m/15m 没有就绪备份、真实待处理年龄达到 **350ms** 时，supervisor 提前发起快照刷新。每组成功准入后至少间隔 1 秒；保留当前业务盘口，依靠水位丢弃随后到达的旧更新，不人为制造故障事件。

所有用途共享同一个 10 秒滑动计数：预热最多用到 24 次、压力刷新最多用到 32 次、故障恢复最多用到 **40 次**，按实际 HTTP 请求计数（两腿算两次），为故障留出额度。预热只在池空闲时启动；预热使用独立的 in-flight 身份和退避时间，**同一连接的预热不得压住真正的故障恢复**。公开 REST 的每 IP `/books` 官方额度为 500 次/10 秒，观察器的上限为其 8%；同 IP 其他进程仍需共同监测。[官方 Rate Limits](https://docs.polymarket.com/api-reference/rate-limits)

新增 `ws_rest_recovery` 的实际 HTTP 并发、warmups、pressure_requests 和有界 worker 延迟样本。延迟包含校验及发布等待，不能解释为纯网络 RTT。

## 3. 压力下的备份就绪

普通队列年龄门槛仍为 1 秒。只有备份在最近 **250ms** 内实际推进过合流盘口 publication，且那次 publication 的接收年龄不超过 1 秒，才临时允许队列/帧接收年龄至 **1.5 秒**。单独收到成交、重复帧或未推进 publication 都不刷新这个资格。

同时增加明确的私有影子与合流水位差上限：每个必需资产最多落后 **750ms**。缺快照、缺时间戳、待订阅、待修复、invalid、resync、delivery_gap 都不能靠宽限通过。缺失业务盘口需要从影子重建时，仍要求影子达到保留水位；已有更新的合流盘口不回滚。提升继续由该连接自己的 worker 执行。

这是一段有实际供数证据的调度宽限，不是把所有积压连接都标成 ready；生产覆盖率和业务缺口改善幅度需要部署后验证。

## 6. 缓存边界

- FeedMerge 的默认单分片去重上限从 16384 降为 4096 条，TTL 从 60 秒改为 **15 秒**。manager 每秒按现有合流器分摊 **8192 条**总预算；八分片通常每片最多 1024 条。新合流器在下一次维护前仍受自身上限约束，不能把“总预算”说成任何瞬间的全进程字节硬上限。
- 连续性 overlap 历史新增全局 **4096 条、30 秒 TTL**，保留每资产 512 条和每条最多四个来源的局部限制。接收时维护总量，supervisor 清掉空闲历史，退订时同步清索引。status 提供 limit、TTL、evictions。
- 不能证明 overlap 时继续记 unverified，不能把淘汰当成恢复了成交。**价位时间水位不按这个 TTL 清除**，避免旧增量覆盖新档位；原有价位数量界限和完整快照收敛仍在。

仅按既有保守计费，8192 条 seen 约 12MiB，4096 条连续性历史约 6MiB；价位水位、latest、滚动样本、解析缓存、队列及诊断仍另占空间。计费不是 RSS。更短窗口/更小条数可能增加跨长延迟副本的重复统计或 overlap 不确定性，须监测，不能声称历史成交已得到完整恢复。

## 7. 100ms 本地证据

新增独立 10Hz 采样线程，不获取 Pipeline / lifecycle 锁，不解析 JSON、不执行 SQL、不每次读取 TCP_INFO。每连接保留最多 100 个样本，约 10 秒，含墙钟、monotonic、采样调度延迟、Linux 加密 TCP Recv-Q、应用队深和真实待处理年龄。reader 额外记录 read_callback 完成耗时。1013 保存本连接及同组对端的序列；status 给出有界窗口的最新值和峰值。

这里是线程式 WS reader，没有 asyncio loop；“延迟”具体指采样线程唤醒延迟及 reader dispatch 耗时，不是交易所延迟或纯网络 RTT。GIL 停顿也可能延后采样，必须结合样本时间间隔判断，不能保证在暂停期间仍准时拿到每个 100ms 样本。

本机 12 个 socketpair、1000 次完整 sampler 调用（含真实 FIONREAD）：CPU **0.04890 秒**，平均每轮 **0.04890ms**，按 10Hz 折合约 **0.049% 单核**，保留样本 1200 个。该短基准不包含完整 WS 业务流量和每帧 dispatch 计时，不代表生产开销保证。

## 9. 风险与获授权部署后的观察指标

1. **每次业务缺口**：逐事件只用最终 `merged_gap_ms` 验收，目标无备份 <1000ms，硬标准仍为 ≤1500ms。按有/无备份、backup/REST、是否压力刷新分桶，不能只看检测至接管时间。网络长尾、冷 TLS、读取超时或 supervisor 锁等待仍可能超过目标。
2. **REST 代价和优先级**：看 warmups、pressure_requests、inflight_http、throttled、failures、worker latency p95/max；核对总数 ≤40/10 秒、同 IP 总额与失败重试。压力刷新是新增默认流量；网络超时或限流时不能用旧预热响应冒充新快照。
3. **备份覆盖**：比较 BTC5m/15m ready ratio、无备份秒数、queue_wait/catchup 阻断、750ms 水位差、实际供数宽限是否短暂有效、resync/drops。宽限不得把长期积压或缺盘口藏起来。
4. **双踢**：保存 source、physical_role、role、promoted_at，核对当前/滚动小时物理次数及业务缺口次数。业务双踢缺口每小时 ≤1；pending 或 capped 必须继续核实，不能当 0。物理静默、未验证成交仍只告警。
5. **1013 前的本地读取**：对齐本路和对端 100ms 字节桶、Recv-Q、调度延迟、reader dispatch、队列年龄，判断是先出现本地停顿还是先关闭。采样缺口本身也要保留；不据单个零队列样本排除短时积压。
6. **内存与 CPU**：跨多个 5m/15m 换期至少观察一小时，联合看 seen entries/capacity/evictions、连续性 entries/TTL/evictions、辅助计费和 RSS 是否平台化；同时观察长延迟重复与 unverified 是否上升。RSS 不回落可能仍有 allocator 高水位，本轮没有改 allocator 或模型。
7. **其余硬标准**：1008 必须为 0；冷门 delivery p95/max 不退化，市场自然静默单列；观察 PG pool exhausted、recording drops 和 PAPER_AUTO，保持实际自动下单关闭。
