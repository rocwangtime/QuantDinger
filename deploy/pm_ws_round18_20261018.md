## 3. CPU、消费延迟与 1013 假设

新增 `backend_api_python/scripts/polymarket_ws_worker_replay.py`，使用真实 MarketConnections、八个 worker、主备合流、影子盘口、supervisor/状态采样及 16MiB 历史缓存。四组热点，主备相差 300ms，每 50ms 一批；20% 帧为双资产完整盘口，每资产 140 档，其余为八行增量；另保留 38 个冷资产历史锚点。每轮 15 秒输入 28,440 物理帧、70,084,376 字节，发布 14,220 条消息，即约 948 条发布消息/秒。

生产 `messages_per_second` 是合流后的发布计数，不能与物理帧混用；它本身还是进程启动以来的平均速率，与瞬时 CPU 的窗口并不完全相同。本轮基准直接以同一窗口的进程 CPU 增量除以实际发布计数增量，同时报告物理帧分母。

原轻量单组回放约 0.083ms/物理帧，负载路径不足以代表生产，未用它宣称达到生产目标。新回放是按生产速率和盘口形状构造的**合成数据**，不是生产原始帧录制；不包含公网 TLS reader、SQL 写入或模型/evaluator 工作。所有 socket 和 HTTP 均在本地替换，纸面模型未运行或改动。

## 4. 按组压力、首次热身与恢复 REST

日志补查：18:21:48，BTC5m 备份已重建 12 次、丢弃 23,372 帧，队龄约 5ms；18:22:19，重建 17 次、丢弃 32,024 帧，队龄 2.042 秒，blockers 含 resync、delivery_gap、queue_wait、catchup，进程 CPU 为 1.138 核。18:22:35 主连接关闭时队龄 6.436 秒；该连接记录的最大处理耗时 116ms、最大解析 76ms、锁等待约 1ms。证据支持累积处理压力及重建反馈，不能指认一次长锁就是 6.4 秒根因。

代码中的放大链是：备份队龄 >2 秒 → 人为设 delivery_gap/resync → 丢弃整队列、清影子 → 请求新快照/REST → 重复消费、再排队。它不要求真实溢出，与生产大量重建、丢帧及 recovery 高请求量相符。仅 warmup 已默认关闭，继续调其频率无法处理这条 recovery 路径。

最终行为：

- **排队久按序追平，不再仅因队龄丢帧重建**。真实溢出、epoch 失效及订阅跨代仍重建；备份原有队龄、快照完整性、750ms 交易所水位差及近期供数宽限均未放宽。
- 心跳采样 scheduler_lag 可同时出现在多路，不再单独作为该路订阅准入压力；须该连接自身待处理年龄 >250ms 才参与阻挡。队列、TCP backlog、resync 等仍按物理连接判定。就绪本来已检查自身队列/水位，本轮没有虚构一个全局 ready 开关，更没有通过移除就绪条件提高比例。
- 首次建立保护前，要求该组主路已拿到带时间戳的完整盘口，待处理年龄 ≤250ms；BTC5m 优先。后续建连继续使用原有全局拨号及订阅预算，其他组不等待某组备份就绪。
- 已建立过保护的组，在故障、换期及主路重新拨号后及时补副本，**不重新套用首次启动等待**。redial 保留 backup_started；所有实际 publication/readiness 闸门继续生效。
- REST 热身继续默认关闭；显式启用时也须主路追平。40/10 秒总预算、后台小时 120 请求上限、真实恢复独立身份和预留容量均保持不变。没有给真正恢复添加小时总量硬帽。

3 秒旧接收时间、但数据完整的队列测试确认：不丢帧、不换 epoch、不重建、HTTP 尝试为 0，收到新鲜完整盘口后重新就绪；真实丢帧测试仍要求新快照。该机制消除了人工队龄重置带来的恢复需求，**不能据此量化生产 recovery 已从约 1600/小时降至约 351/小时**。新的 `ws_pressure_scope`、`ws_backup_queue_lag_action` 说明状态口径。

## 5. 2019ms 与 324/553ms 的统一

原主故障事件在检测时已经记录约 2019ms 的合流接收静默下界，并持续取较大值；逐资产 business gap 却由提升后的 switch/snapshot 阶段注册，在后续 publication 时取一段较短的相邻接收间隔。18:22 日志中的 324/553ms 因此是后半段，不能覆盖完整故障窗口。

**验收保留 2019ms 失败，不用 324/553ms 把该次改判通过。** 旧材料不足以逐笔重建唯一精确值；本轮以统一 incident 的最终值作为后续依据。

现在故障检测先冻结各资产的合流接收基线，注册 incident，再发起 REST，且不等待昂贵的 Pipeline 锁才派发 HTTP。FeedContinuity.publication 按同一 incident 跟踪各腿，保留检测时静默下界及恢复间隔；各腿收到故障检测之后的新接收时间才最终完成。事件标明 `merged_gap_scope=incident_receipt_cadence`，最终 `merged_gap_ms` 为各腿最大值，完成后冻结。

`Polymarket WS business gap` 日志包含 incident_id 和逐资产最终值，与事件汇总同源；原局部记录改名为 `continuity phase gap`，scope 为 switch_phase_receipt_cadence，不能混作整次验收。没有基线或未完成的腿保持未知/未完成，不能当通过。pending incident 每资产最多 64 个，资产移除时清理，并计入保守内存估算。

测试覆盖旧数据追平、逐腿恢复、静默下界不被 324ms 局部间隔抹掉、最终汇总与逐资产日志一致、恢复完成后冻结、未知基线、容量及移除边界，以及 HTTP 早于 Pipeline 锁的要求。物理源缺口和历史成交口径未改成失败项。

## 6. TLS 与提升竞态

确认的本地风险：旧 retire/PONG/错误路径从控制线程调用 WebSocket.shutdown，直接关闭描述符；SSLSocket.shutdown 又会清除 SSL 对象。这会与仍在 recv/send 的线程并发，描述符随后可能交给新连接。现在控制线程停止心跳，只调用基础 socket 的系统层 shutdown 唤醒 reader，不关闭或复用描述符、不清除 SSL 对象，最终 TLS teardown 由 reader 完成；没有放宽证书验证，也没有修改代理或地区设置。

全量测试另抓到一个真实可见性窗口：新主连接已写入 states，旧连接却要在日志/指标调用之后才 retired。现在先使旧连接 retired/invalid，再暴露新主连接。确定性回归在此处暂停 worker，验证旧回调不会影响新主连接；另测提升后补备份、旧 TLS 错误迟到、系统层中断保留 SSL 对象与描述符所有权。

**不能确认生产两次年龄为 0 的 WRONG_VERSION_NUMBER 都由这些竞态引起**，原日志缺少握手阶段堆栈。新增 `transport_phase` 区分 tls_or_http_upgrade、subscription、subscribed；回归验证 pre-open SSL 错误不会记成 1013 或主路故障。若真正在 upgrade 阶段再现，仍需继续定位，不能宣称该外部错误已消失。

## 8. 风险及获授权部署后的观察

1. 同一窗口累计 CPU 增量/合流消息增量是否 ≤0.6ms；同时看物理帧速率、parse/process/lock/lifecycle 等耗时及主备 queue_wait 长尾。离线降幅较小、负载路径不完整，不能预测生产 CPU 降幅。
2. 按 incident_id 检查逐腿最终值与 hot_primary_failures 汇总一致、每次 ≤1500ms；未最终完成/未知不能算通过。采集方需区分新 incident business gap 与旧 continuity phase。主备双踢业务缺口仍须每小时 ≤1，1008 必须为 0。
3. BTC5m 及其他热门组的 without_ready_backup 增量，目标被踢时零就绪为 0；ready ratio 目标 0.89–0.96。启动若主路缺快照或持续积压，会等待首次备份准入，需观察该段失备时间；没有用放宽就绪门槛消除它。
4. 三类 REST 实际 HTTP/小时、恢复耗时、throttled/deferred/failures；目标总量接近 round15 约 351/小时，但真实故障必须及时恢复。交叉核对 resync 原因、真实 overflow、缺快照及 epoch 变化，确认人工队龄重建流量消失。
5. 不再因单纯队龄重置后，持续处理能力不足仍可能使备份长时间不就绪，并最终碰到原有队列字节/数量上限。保留真实溢出恢复；重点看内存、队龄是否平台化，不能只看丢帧减少。
6. 启动前两分钟、提升/重新拨号后新备份的 TLS phase、连接年龄、SSL reason；两次生产 WRONG_VERSION_NUMBER 的精确根因仍未证实。开发期异常回放亦保留为未关闭风险。
7. RSS、history ≤16MiB、辅助缓存及淘汰，跨多次换期至少观察一小时。新增小时间戳缓存及 incident 均有界；本轮没有证明整个生产进程无泄漏。
8. 冷门看交付延迟，物理静默 >20s、成交明细缺失继续只告警；同时确认 PG、recording drops、PAPER_AUTO=0、纸面订单/库存及所有原闸门。
