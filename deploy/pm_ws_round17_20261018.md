## 3. REST 暴增根因与修复

代码可确认的原因：

1. 四个热门主路约每 15 秒各做一次热身，两 token 往往拆成两个 HTTP 请求。仅此理论流量就约 1920 请求/小时，已明显高于 round15 约 351 请求/小时的整个恢复流量。
2. 压力触发只看物理队列 ≥350ms、没有就绪备份；不检查合流业务是否仍被另一条流推进。持续积压时每组约每秒重拉，两腿又分开，形成额外流量。
3. 压力刷新和真实恢复共用 in-flight 身份及 `rest_retry_at`。压力任务可能压住同状态的故障请求；多个后台任务还可能占满四个槽位。
4. 预算拒绝后没有设置拒绝退避，约 200ms 一轮的 supervisor 可反复撞相同额度。槽位不足也被旧总 throttled 计入，因此它不能解释为上游限流。
5. 备份自动缺快照重试可能在 WS 补齐后仍执行；原路径先清影子盘口再拉 REST。拒绝后的修复意图又会被弹出，需等下一次扫描重新发现。

最终行为：

- **定时热身默认关闭**：新配置 `POLYMARKET_OBSERVER_WS_REST_WARM_SECONDS=0`。设为正数可启用，实际周期至少 60 秒；必须本路无订阅压力、HTTP 池空闲，且全池最近至少 60 秒没有准入 HTTP 请求。双 token 热身仍可预热两个会话，响应不发布、不作为故障缓存。
- 压力刷新保留，但必须同时满足：BTC 物理积压 ≥350ms、至少一个当前资产的真实合流发布时间已老 ≥700ms、无就绪备份、当前积压段尚未成功触发。两腿放进一个 `/books` 请求。成功后至少间隔 30 秒；持续不排空的积压段只触发一次，队列回到 350ms 以下才允许进入下一段。拒绝尝试也设置重试时间。
- recovery / warmup / pressure 分别拥有身份与冷却，后台任务不能压住同状态的真正恢复。后台最多一个逻辑任务，准入后保留至少两个 HTTP 槽位；真实恢复仍可两腿并行，槽位不足时保留原有批量退路。
- 保留总计 40/10 秒、热身 24/10 秒、压力 32/10 秒的原预算层级，为恢复保留至少八个滑动窗口额度。新增后台合计 **120 个实际 HTTP 请求/滚动小时** 的硬上限，双腿热身必须整体放得下剩余额度；该小时限额不限制 recovery。
- 预算拒绝退避至窗口释放；重复 single-flight / 冷却触发不会反复记一次限流。恢复槽位不足仍保留本地 throttled 计数，并记录 deferred，没有靠改名把真实准入拒绝清零。
- 缺快照恢复被拒绝时保留修复意图。自动“缺盘口”工作重新核对当前影子；WS 已补齐则取消过时请求。显式连续性恢复、真实 delivery_gap、旧 epoch / invalid / resync 的要求保留，不使用旧影子冒充新快照。

正常合流持续推进时，默认新增热身与压力 HTTP 流量为零；26 项专项包含 18000 次虚拟 supervisor 调用、覆盖一小时调度跨度的健康场景，未产生后台 HTTP。这个验证说明新增后台轮询已消除，**不保证真实恢复需求的小时总数固定等于 round15**。

## 4. 备份就绪率与调度

round16 新增 750ms 的影子/合流水位差条件；压力 REST 又会把合流水位提前推到更近的快照时间，排队的影子更容易暂时 catchup 不足。自动缺盘口重试在补齐后再次清空影子，会延长缺快照和不就绪阶段。以上是代码层面的放大路径；日志不足以量化每条路径对 2.03 秒排队的占比。

`ingress_pressure` 是 prepare_stage 的诊断标签；永久热门备份的 `backup_ready` 并不直接依赖订阅热身的 `settled()`，不能把这个标签直接归因为新增热身准入闸门。这里是 reader / worker / supervisor 线程结构，不是 asyncio 事件循环。

本轮通过减少后台 HTTP/发布、合并压力批次、取消过时自动修复来降低争用；没有放宽 750ms 水位差、1 秒普通队列门槛、仅限近期实际供数的 1.5 秒宽限，也没有取消真实丢帧的重建。

本地补充突发验证：每路 320 帧、2,202,240 字节，每个 book 含 96 档，50ms 最大突发 110,112 字节；备份排队采样峰值 **20.82ms**，就绪采样 **100%**，resync=0、HTTP=0。这是未启 SQL 写入和纸面历史的轻量 fixture，不包含生产完整业务负载，也不能作为公网或生产 ready ratio 保证。另有提交的双流排队测试，验证无秒级队列、无重建及不触发额外 REST。

## 5. BTC5m 1013 与拆分评估

证据仍支持服务端单连接突发发送缓冲压力这一解释：外部 ss Recv-Q 峰值 ≤18KB、Send-Q=0、无重传，突发 1 秒约 380–527KB，100ms 峰值约 145–236KB，关闭前停发约 0.7–0.8 秒。但采样不能排除全部短时本地停顿，也没有官方 market 缓冲上限可据以证明根因。

只拆 BTC5m Yes/No 且每腿保持主备，稳态将从该组两条 WS 增至四条，**增加两条连接**，通常增加两个 reader、两个 worker、两个 FIFO；按现有单 FIFO 16MiB 计费上限，额外队列理论计费容量最多 32MiB，另有线程、socket 和影子开销，不等于 RSS 增量。总资产副本数不变，单连接峰值有望下降，但不能保证减半或消除 1013。

## 6. 内存结论

生产样本 RSS 从 143MiB 到 176MiB，但 history 计费并非单调上升：例如约 12.0→3.8→13.9→11.8→10.2→13.7MiB；辅助缓存约 18.3–25.8MiB 来回变化。history 保留 10 秒事件及折叠盘口锚点，热门完整快照/增量会快速填满 16MiB 保守计费预算；达到预算后折叠最旧事件，过旧回放失败关闭。6674 次按字节淘汰本身说明预算在工作，不是已证明的泄漏。

连续 80000 条事件的独立合成验证中，历史计费始终 ≤16MiB，稳态保留约 3695 条，累计按字节淘汰 76313 次。第 10000 到第 80000 条 RSS 为 67,604,480→67,620,864 字节，仅增加 **16KiB**；Python 跟踪的活对象约 8.91MB，保持平台。空闲过期后历史条数和计费都为 0，Python 活对象降到约 1.27MB，RSS 仍约 66.6MB，呈现分配器高水位特征。

该实验支持 BookHistory 有界并能释放活对象，不能证明生产整个进程只存在热身高水位。队列、解析缓存、去重、线程和其他业务对象仍须观察至少一小时、跨多次换期。本轮**不调整生产 history 的 16MiB 上限或淘汰策略**，避免进一步缩短可用回放窗口；新增饱和与空闲过期测试。新增 REST 统计最多 3600 个秒桶，后台时间戳最多 120 条，均有界。

## 7. status 新字段及口径

`ws_rest_recovery.categories.{recovery,warmup,pressure}` 各有 `total` 与 `rolling_hour`，含 `attempts / requests / completed / failures / throttled / deferred`：

- `requests` 按实际准入 HTTP 数计，两腿并行算两次；原 warmups / pressure_requests 仍为逻辑任务数，保留兼容。
- `attempts` 不计 single-flight / 冷却早退；`throttled` 是本地预算或恢复槽位准入拒绝，不能当上游 429。后台让位、空闲条件不满足计 deferred；容量场景可能同时计 throttled 与 deferred，不能相加作为独立请求总数。
- 滚动小时使用 monotonic 秒桶，最多 3600 桶，边界精度为一秒，空闲时读取 metrics 也会过期；另有 `background_limit_per_hour=120`、`reserved_recovery_slots=2`。

热门组覆盖行新增 `unready_reasons`、`unready_reason_seconds`、`unready_reason_entries`，包括 catchup、queue_wait、missing_snapshot、snapshot_repair、ingress_pressure、no_backup 等。按组无就绪备份时的状态变化积分，不依赖外部 30 秒状态抽样；多个原因可重叠，秒数不能相加成总失备时间。当前 ready 时原因清空，持续时间保留累计。未改变既有业务缺口验收口径。

## 9. 风险及获授权部署后的观察

1. 逐事件最终业务合流缺口 ≤1500ms；主备双踢业务缺口每小时 ≤1；pending / capped 仍不能算通过。1008 必须为 0，物理静默与成交明细缺失继续只告警。
2. 三类 REST 每小时实际 HTTP 数、throttled、deferred、failures、HTTP 并发和恢复延迟。稳态新增后台流量应接近 0，总量目标回到 round15 约 351/小时附近；真正缺快照不得为了凑总数而不恢复。按故障、自动缺盘口、压力段交叉核对，不以逻辑 warmups 代替实际 HTTP 数。
3. 四热门组 ready ratio 目标恢复至 0.89–0.96 或更高；联合看 queue_wait p95/max、catchup/ingress_pressure 原因秒数、resync/丢弃和切换时 ready_backup_at_kick，不把门槛放宽当作改善。生产若仍有秒级排队，本轮尚不能宣称目标完成。
4. 默认关闭热身可能使低频恢复遇到冷 TLS；真实恢复仍保持两腿并行与原连接/读取超时。后台压力的批量响应可能被慢腿拖慢，但不占恢复身份或冷却。极端多组同时恢复仍可能用满四个槽位及 40/10 秒预算，预留不是无限容量承诺。
5. 持续积压段只做一次压力刷新；失败或长时间不排空时不会不断重复刷新。真实故障和缺快照恢复独立继续执行，需观察业务新鲜度是否仍可维持，不能把预防刷新失败隐藏起来。
6. BTC5m 1013 按物理连接年龄、单连接 100ms/1s 字节、Recv-Q、reader dispatch、sampler lag 对齐观察；本轮没有部署拆分方案，不能承诺减少 1013 次数。
7. RSS、history/auxiliary 计费、淘汰、解析缓存、线程与队列跨多个换期观察至少一小时。若活对象与 RSS 持续同时增长，再定位具体持有者；不能仅以 RSS 不立即回落认定泄漏，也不能仅以缓存有界排除别处泄漏。
8. 冷门 delivery p95/max、PG pool、recording drops、纸面库存及 PAPER_AUTO 一并确认。PAPER_AUTO 保持关闭。
